两套方案的核心差别，不只是“React 还是 Next.js”，而是：
- 方案 A：腾讯 CloudBase 一体化，优先快速交付和国内稳定访问。
- 方案 B：Next.js + Vercel + PostgreSQL，优先完整工程能力和 Agent SDK 兼容性。
总体比较
维度	CloudBase 方案	Next.js + Vercel 方案
前端	React + Vite	Next.js App Router
后端	CloudBase 云函数	Next.js Route Handlers
数据库	CloudBase 文档数据库	Neon/Supabase PostgreSQL
部署	CloudBase 静态托管	Vercel
国内访问	相对更稳	存在评委打不开的风险
开发复杂度	较低	中等偏高
AI 流式交互	需要自己封装	Next.js/Vercel 支持更自然
Agent SDK	尚未验证	独立探针中已经跑通
关系型数据	一般	很强
向量检索	需要额外设计	pgvector 比较成熟
运维组件	基本一个平台	Vercel + 数据库 + Blob 等多个平台
比赛期风险	平台学习和 AI 接入	网络、打包体积、连接池和函数限制
工程展示力	足够	更强，但也更容易过度设计


CloudBase 官方提供数据库、身份认证、云函数、文件存储和静态网站托管，可以用一套服务完成整个应用。CloudBase 官方文档
Vercel 对 Next.js 的支持更加原生，但函数存在 4.5 MB 请求/响应限制、250 MB Node 函数包限制等约束；默认计算区域也是美国，需要手动调整到香港等区域。Vercel 函数限制、Vercel 区域说明
方案 A：React + Vite + CloudBase
优点
- 上线最快
  前端是普通 SPA，后端使用云函数，无须处理 Next.js 服务端组件、缓存和 Server Actions。
- 国内访问风险更低
  对比赛现场和深圳评委更友好，这是非常现实的优势。
- 基础设施集中
  登录、数据库、函数、文件存储和部署都在 CloudBase，不需要管理多个服务账号和连接池。
- 很适合现在的业务
  用户画像、测评答案、学习计划、导师资料都很适合文档型数据结构，例如：
{
  "userId": "123",
  "major": "计算机科学",
  "interests": ["人工智能", "机器人"],
  "assessment": {
    "researchLevel": 2,
    "paperReadingLevel": 1
  },
  "currentPlan": []
}
- 更容易做稳定 Demo
  你们的核心是表单、资料检索、AI 生成和成长记录，不需要复杂的服务端渲染或 SEO。
缺点
- CodeBuddy Agent SDK 尚未验证
  之前只验证了它在 Vercel 函数中的运行情况，不能直接假设在 CloudBase 云函数中同样能跑。
- 文档数据库长期扩展不如 PostgreSQL
  如果以后要做复杂的导师—实验室—论文—领域关系、统计分析和高级检索，关系型数据库更舒服。
- AI 流式响应要额外处理
  普通问答没问题，但如果想实现 ChatGPT 式逐字输出，需要专门验证云函数和前端的流式链路。
- 切换平台有迁移成本
  如果团队已经写了较多 Next.js/Vercel 代码，现在迁移反而会拖慢进度。
方案 B：Next.js + Vercel + PostgreSQL
这是[原决策记录](C:/Users/30888/Downloads/项目决策记录.md)里的方案。
优点
- 前后端统一
  Next.js 页面、接口和服务端逻辑都在同一个项目中，TypeScript 类型可以复用。
- AI Web 应用体验更好
  Route Handlers 很适合构建聊天接口、流式输出和工具调用。Next.js 官方也将其定位为构建全栈应用的能力。Next.js 官方文档
- Agent SDK 有实测基础
  决策记录里已经有独立探针证明 CodeBuddy Agent SDK 能在 Vercel 函数中运行，这是该方案最大的独特优势。
- PostgreSQL 数据模型更规范
  比较适合这些关系：
导师 ── 所属 ── 实验室
导师 ── 研究 ── 研究方向
实验室 ── 发布 ── 招募信息
用户 ── 感兴趣 ── 研究方向
用户 ── 完成 ── 学习任务
- pgvector 扩展方便
  将来做导师匹配、知识库检索和相似论文推荐时更自然。
- 工程展示力更强
  在 PPT 中能够展示完整的全栈架构、适配器层、模型工具调用和关系型知识库。
缺点
- 国内访问是最大风险
  即使函数放在香港，*.vercel.app 的实际访问情况仍需要用不同网络实测。评委打不开链接比技术少一个功能严重得多。
- 架构偏重
  Vercel、PostgreSQL、pgvector、Blob、Agent SDK、CLI 打包一起上，8 天内很容易把时间花在基础设施上。
- Agent SDK 打包存在技术风险
  CLI 二进制可能接近 Vercel 函数包限制，而且主项目还没有完成同样的复现。
- Serverless 数据库连接更复杂
  必须使用连接池，还要考虑冷启动、连接数和数据库区域与函数区域的距离。
- 之前的部分选型不适合当前项目
  决策记录中的 PDF 解析、知识图谱可视化、Blob 上传等，明显来自此前的论文/知识图谱候选方案。“科研小助理”首版不需要全部继承。
双轨 Web + Skill/专家包
这与基础技术栈是另一项决策。
优点
- 能证明作品与 LearnBuddy/CodeBuddy 平台深度结合。
- 可作为运行时 AI 合规问题的对冲。
- 提示词、方法论和科研训练流程可以沉淀为可复用 Skill。
- PPT 中比较有故事性：“一个科研成长方法论，两种使用载体”。
缺点
- Skill/专家包不能替代在线 Web 链接。
- 评委大概率不会安装，主要价值只是材料展示。
- “只增加 10%～15% 工作量”偏乐观，还要制作安装说明、截图、录屏和验证包。
- Web 没完成前做双轨，会明显分散注意力。
我的倾向是：先不把双轨列为必做。Web 产品稳定后，如果还剩半天到一天，再把已经成熟的 Prompt 和方法论封装成 Skill。
我的最终倾向
如果主项目还没有正式开发
我倾向于：
React + Vite + TypeScript + CloudBase，先完成稳定可用的比赛 MVP。

理由是：
1. 你们现在的产品不需要 SSR 和 SEO。
2. 数据以用户档案、测评、任务和导师资料为主，文档数据库足够。
3. 国内访问和现场稳定性比架构高级更重要。
4. 基础设施少，能把时间投入产品闭环、导师数据和用户体验。
5. 腾讯云技术栈与比赛背景一致，但要注意：这不代表官方一定额外加分。
技术栈可以收敛成：
React + Vite + TypeScript
Tailwind CSS + shadcn/ui
CloudBase Auth
CloudBase 文档数据库
CloudBase 云函数
CloudBase 静态托管
一个可替换的 LLM Adapter
第一版不要上：
- pgvector
- 自动爬虫
- PDF 批量解析
- 知识图谱
- 多智能体
- 自动邮件发送
- 复杂 Skill 市场分发
如果 Next.js 主项目已经写了较多代码
那就不要迁移，继续：
Next.js + Vercel + PostgreSQL，但大幅削减不必要组件。

具体削减为：
- 保留 Next.js、Vercel、PostgreSQL和模型适配器。
- 暂不做 pgvector，先用标签和 SQL 查询。
- 暂不使用 Blob，除非确实需要用户上传文件。
- 暂不做知识图谱可视化。
- Agent SDK 只做一条最小演示链路，不要让所有功能都依赖它。
- 准备国内可访问的静态或 CloudBase 备用演示页。
一句话结论
如果从零开始，我选 CloudBase，因为比赛期最重要的是“稳定上线并跑通完整体验”；如果 Next.js 代码和 Agent SDK 链路已经在主项目中形成，则保留 Next.js/Vercel，避免临时换栈，但必须解决国内访问并砍掉过度设计。
