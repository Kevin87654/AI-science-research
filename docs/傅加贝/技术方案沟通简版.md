# 科研小助理技术方案沟通简版

## 1. 当前结论

我们计划开发一个面向大一新生的科研成长 Web 应用，帮助学生完成：

- 科研认知测评
- 个人科研画像
- 个性化学习路线
- 科研基础知识问答
- 深圳大学实验室与导师公开信息检索
- 论文阅读与写作训练
- 科研简历和联系导师材料生成
- 科研成长记录

第一版的目标不是实现所有设想，而是优先做出一个可以在线访问、流程完整、演示稳定的比赛作品。

推荐技术组合：

```text
React + Vite + TypeScript
        │
        ▼
CloudBase 静态网站托管
        │
        ▼
CloudBase HTTP 云函数
        ├─ 单 Agent + 工具调用
        ├─ CloudBase AI
        ├─ 文档型数据库
        ├─ 身份认证
        └─ 云存储
```

## 2. 为什么选择这套方案

### 落地快

前端、后端、数据库、登录、AI 和部署尽量集中在 CloudBase，减少同时维护 Vercel、PostgreSQL、对象存储等多个平台的成本。

### 比赛访问更稳

评委需要直接打开在线链接体验。相比海外托管平台，腾讯云服务在国内访问方面更适合作为比赛主方案。

### 够用且不过度设计

当前主要数据是用户档案、测评答案、学习计划、导师和实验室资料，文档型数据库已经能够满足第一版需求。暂时不需要 PostgreSQL、pgvector、知识图谱或复杂的多智能体系统。

### 方便后续替换模型

AI 调用统一放在后端，并通过适配器封装。若组委会后续明确要求特定模型或 LearnBuddy 运行方式，只需要替换 AI Provider，不必重写前端和业务逻辑。

## 3. Web 产品如何运行

核心用户流程：

```text
进入产品
  ↓
完成科研认知测评
  ↓
生成个人科研画像
  ↓
获得个性化学习路线
  ↓
学习科研、论文和比赛基础知识
  ↓
检索实验室与导师公开资料
  ↓
完成论文阅读或写作训练
  ↓
生成科研简历和联系导师材料
  ↓
保存科研成长记录
```

评委应当能在几分钟内体验上述主要流程，不依赖开发者现场操作。

## 4. Agent 的实现方式

第一版只做一个主 Agent，不做多个 Agent 互相讨论。

主 Agent 根据用户请求调用不同工具：

```text
research_assistant
├─ 读取用户科研档案
├─ 分析测评结果
├─ 检索科研基础知识
├─ 检索实验室和导师
├─ 检索科研比赛
├─ 生成学习路线
├─ 提供论文训练反馈
├─ 生成科研简历和联系导师材料
└─ 保存学习进度
```

这已经具备智能体的核心特征：能理解目标、读取个人状态、调用工具、使用可靠资料并保存结果。

## 5. 数据准备方式

比赛版不优先开发自动爬虫。实验室、导师、科研比赛等资料采用人工收集和结构化整理，来源包括学校官网、学院官网、实验室官网及教师主页。

每条资料至少记录：

- 名称与简介
- 学院或所属单位
- 研究方向或适用专业
- 原始来源链接
- 收集或核验日期
- 是否经过人工核验

所有回答应尽可能展示资料来源，避免生成未经证实的导师评价。

## 6. 第一版重点功能

优先级从高到低：

1. 科研认知测评和个人科研画像
2. 个性化科研学习路线
3. 科研知识问答
4. 实验室与导师公开信息检索
5. 科研成长记录
6. 论文阅读和写作训练
7. 科研简历与联系导师材料生成

如果开发时间不足，必须优先保证前五项组成完整闭环，后两项可以做成简化版本。

## 7. 当前明确不做

为避免范围失控，第一版暂不开发：

- 多智能体协作
- 自动爬取全校导师资料
- PostgreSQL 和 pgvector
- 论文 PDF 批量解析
- 知识图谱可视化
- 自动向导师发送邮件
- 导师主观评分或负面评价
- 全自动论文代写
- 与 Web 同时开发完整 Skill 或专家包

这些内容可以放入未来规划，但不能阻塞 Web 主产品上线。

## 8. AI 与合规原则

- 模型密钥和系统提示词只放在后端。
- AI 生成的学习路线、简历和邮件必须允许用户修改确认。
- 产品定位为科研启蒙、训练和反馈工具，不提供论文代写。
- 不伪造实验数据、论文、参考文献或导师评价。
- 导师和实验室信息以公开来源为准，并显示出处。
- 持续保留 LearnBuddy 在需求分析、设计、编码、调试和测试中的使用记录。

组委会对 Web 运行时 AI 来源的口径仍需进一步确认，因此后端必须保留模型适配器，避免绑定单一模型。

## 9. 技术栈清单

| 模块 | 选择 |
|---|---|
| 前端 | React、Vite、TypeScript |
| UI | Tailwind CSS、shadcn/ui |
| 路由 | React Router |
| 请求管理 | TanStack Query |
| 表单校验 | React Hook Form、Zod |
| 后端 | CloudBase HTTP 云函数、Node.js、TypeScript |
| 数据库 | CloudBase 文档型数据库 |
| 登录 | CloudBase 匿名登录，后续可绑定邮箱 |
| AI | CloudBase AI，后端统一调用 |
| 存储 | CloudBase 云存储 |
| 部署 | CloudBase 静态网站托管 |
| 代码仓库 | GitHub 或 Gitee |

## 10. 团队当前需要达成的共识

1. Web 应用是唯一的主交付，其他封装形式只能作为补充。
2. 先完成稳定的核心闭环，再增加论文训练、简历等扩展功能。
3. 不把时间消耗在多智能体、向量数据库和知识图谱等非必要技术上。
4. 导师和实验室资料必须有可靠来源，不能让 AI 自行编造。
5. AI 调用使用统一适配器，为后续模型切换和赛事合规调整留出空间。
6. 所有开发过程及时保留 LearnBuddy 使用记录，作为最终必交材料和评分证据。

## 11. 仍需尽快确认的问题

- 组委会是否允许 Web 运行时使用 CloudBase AI 或其他模型接口。
- LearnBuddy 是否提供适合 Web 作品调用的正式 API。
- 提交页面中的 Skill 包是否为必需材料或可选加分材料。
- 团队实际能够收集并核验多少实验室和导师资料。

在这些问题确认前，Web 的前端、数据库和业务流程可以正常开发，AI 层通过适配器保持可替换。
