# 科研小助理技术方案沟通简版

> 更新：2026-09-19，采用 Vercel 主体、CloudBase PostgreSQL 和匿名会话方案 A。

## 1. 当前结论

我们计划开发一个面向大一新生的科研成长 Web 应用，帮助学生完成：

- 科研认知测评
- 个人科研画像
- 个性化学习路线
- 科研基础知识问答
- 深圳大学实验室与导师公开信息检索
- 论文阅读与写作训练
- 科研简历和联系导师材料生成
- 科研成长记录

第一版的目标不是实现所有设想，而是优先做出一个可以在线访问、流程完整、演示稳定的比赛作品。

推荐技术组合：

```text
Next.js + TypeScript
        │
        ▼
Vercel（hkg1）
        │
        ▼
Next.js Route Handlers
        ├─ 任务编排器 + 工具调用
        ├─ 规则引擎与模板
        ├─ 可选 AI Provider（默认关闭）
        ├─ 匿名会话方案 A
        └─ CloudBase Repository
                    │
                    ▼
        CloudBase PostgreSQL / PostgREST
```

## 2. 为什么选择这套方案

### 主体开发和部署顺畅

组委会已经确认 Vercel 可以用于作品链接。Next.js 页面、API 和匿名会话放在同一个 Vercel 项目中，便于 Git 自动部署、预览和排错。

### 复用已验证的腾讯云数据库

CloudBase PostgreSQL 的 HTTP CRUD 和 pgvector 已被组员实测跑通。Vercel 服务端通过 PostgREST 访问数据库，不需要 PostgreSQL 连接池，也不新增 Neon 或 Supabase。

### 够用且不过度设计

当前主要数据是用户档案、测评答案、学习计划、导师和实验室资料。使用现有 CloudBase PostgreSQL 即可；第一版暂不启用 pgvector、知识图谱或复杂的多智能体系统。

### 不依赖实时外部模型

现阶段赛事答复对 Web 运行时外部模型的口径是“建议不用”，因此提交版默认采用规则引擎、模板和可信资料检索。AI Provider 仍保留为默认关闭的可选增强；若后续获得明确许可，可以启用而不重写前端和业务逻辑。

## 3. Web 产品如何运行

核心用户流程：

```text
进入产品
  ↓
完成科研认知测评
  ↓
生成个人科研画像
  ↓
获得个性化学习路线
  ↓
学习科研、论文和比赛基础知识
  ↓
检索实验室与导师公开资料
  ↓
完成论文阅读或写作训练
  ↓
生成科研简历和联系导师材料
  ↓
保存科研成长记录
```

评委应当能在几分钟内体验上述主要流程，不依赖开发者现场操作。

## 4. 任务编排与可选 Agent

第一版使用受控任务编排器，不做多个 Agent 互相讨论，也不要求实时大模型参与主链路。

编排器根据页面场景、用户动作和轻量意图规则调用不同工具：

```text
research_assistant
├─ 读取用户科研档案
├─ 分析测评结果
├─ 检索科研基础知识
├─ 检索实验室和导师
├─ 检索科研比赛
├─ 生成学习路线
├─ 提供论文训练反馈
├─ 生成科研简历和联系导师材料
└─ 保存学习进度
```

它能够读取个人状态、调用工具、使用可靠资料并保存结果。若后续获得明确许可，可在相同工具接口上启用 LLM Agent，核心业务和数据层无需修改。

## 5. 数据准备方式

比赛版不优先开发自动爬虫。实验室、导师、科研比赛等资料采用人工收集和结构化整理，来源包括学校官网、学院官网、实验室官网及教师主页。

每条资料至少记录：

- 名称与简介
- 学院或所属单位
- 研究方向或适用专业
- 原始来源链接
- 收集或核验日期
- 是否经过人工核验

所有回答应尽可能展示资料来源，避免生成未经证实的导师评价。

## 6. 第一版重点功能

优先级从高到低：

1. 科研认知测评和个人科研画像
2. 个性化科研学习路线
3. 科研知识问答
4. 实验室与导师公开信息检索
5. 科研成长记录
6. 论文阅读和写作训练
7. 科研简历与联系导师材料生成

如果开发时间不足，必须优先保证前五项组成完整闭环，后两项可以做成简化版本。

## 7. 当前明确不做

为避免范围失控，第一版暂不开发：

- 多智能体协作
- 自动爬取全校导师资料
- 主动引入新的数据库或独立向量数据库
- 论文 PDF 批量解析
- 知识图谱可视化
- 自动向导师发送邮件
- 导师主观评分或负面评价
- 全自动论文代写
- 与 Web 同时开发完整 Skill 或专家包

这些内容可以放入未来规划，但不能阻塞 Web 主产品上线。

## 8. AI 与合规原则

- 提交版默认不启用实时外部模型。
- 如果后续获准启用，模型密钥和系统提示词只放在后端。
- AI 生成的学习路线、简历和邮件必须允许用户修改确认。
- 产品定位为科研启蒙、训练和反馈工具，不提供论文代写。
- 不伪造实验数据、论文、参考文献或导师评价。
- 导师和实验室信息以公开来源为准，并显示出处。
- 持续保留 LearnBuddy 在需求分析、设计、编码、调试和测试中的使用记录。

现阶段已知口径是：Web 运行时外部模型“建议不用”；LearnBuddy Web API 不明确且不建议依赖；CodeBuddy CLI/Agent SDK 是否属于认可能力未知；Skill 包为可选项；方向二是否必须开源仍未知。后端继续保留默认关闭的模型适配器，但核心功能不得依赖它。

## 9. 技术栈清单

| 模块 | 选择 |
|---|---|
| 全栈框架 | Next.js App Router、TypeScript |
| UI | Tailwind CSS、shadcn/ui |
| 表单校验 | React Hook Form、Zod |
| 后端 | Next.js Route Handlers / Vercel Functions |
| 数据库 | CloudBase PostgreSQL 17 |
| 数据访问 | PostgREST + Repository 适配器 |
| 登录 | Vercel 服务端匿名会话方案 A |
| AI | 可选 Provider，默认关闭；获准后再由后端统一调用 |
| 存储 | P0 暂不引入独立存储 |
| 部署 | Vercel，函数区域 `hkg1` |
| 代码仓库 | GitHub 或 Gitee |

## 10. 团队当前需要达成的共识

1. Web 应用是唯一的主交付，其他封装形式只能作为补充。
2. 先完成稳定的核心闭环，再增加论文训练、简历等扩展功能。
3. 不把时间消耗在多智能体、向量数据库和知识图谱等非必要技术上。
4. 导师和实验室资料必须有可靠来源，不能让 AI 自行编造。
5. 核心流程使用规则和模板；可选 AI 使用统一适配器并默认关闭。
6. 所有开发过程及时保留 LearnBuddy 使用记录，作为最终必交材料和评分证据。
7. CloudBase API Key 只能存在于 Vercel 服务端，前端不得直接访问数据库。
8. 用户身份只来自 HttpOnly 匿名会话，不能相信前端传入的 `userId`。

## 11. 赛事口径与项目处理

| 问题 | 当前答复 | 项目处理 |
|---|---|---|
| Web 运行时外部模型 | 建议不用 | 提交版默认关闭 |
| 第三方 AI 是否只是建议 | 建议不用 | 不作为必需链路 |
| LearnBuddy Web API | 不知道，但不建议依赖 | 不等待、不假设存在 |
| CodeBuddy CLI/Agent SDK 合规性 | 不知道 | 仅做可选验证 |
| Skill 包 | 可选项 | Web 完成后有余力再做 |
| 方向二是否必须开源 | 不知道 | 仍按可开源标准准备 |

团队还需确定实际能够收集和核验多少实验室、导师及比赛资料。在赛事口径进一步明确前，Web 的前端、数据库、规则引擎和业务流程可以正常开发。

## 12. 当前最大的技术风险

- CloudBase API Key 权限较高，必须只放在 Vercel 服务端，并验证最小权限和轮换流程。
- 所有私有数据查询必须从匿名会话取得 `userId`，防止越权读取他人画像和简历。
- 匿名 Token 使用 HttpOnly Cookie，数据库只保存哈希；修改请求还要校验 Origin/CSRF。
- Vercel `hkg1` 到 CloudBase 上海的真实延迟尚未验证，D1 必须跑线上 CRUD 探针。
- PostgREST 查询参数必须白名单化，禁止前端传入原始过滤表达式。
- 多表事务通过 PostgreSQL RPC 完成，不能由 Vercel 连续发送多个 HTTP 请求模拟事务。
- Vercel Preview 不得默认连接生产数据库，避免测试代码污染正式数据。
- 实时 AI 默认关闭，CodeBuddy CLI 跑通不代表适合进入比赛主链路。
