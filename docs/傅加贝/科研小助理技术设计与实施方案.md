## 1. 文档目的

本文将“面向大一新生的科研小助理”整理为一套可实施的 Web 技术方案，覆盖：

- 产品边界与核心用户流程
- 技术栈与架构选择
- 前后端模块划分
- 数据模型与内容数据规范
- Agent、模型适配器与工具调用设计
- API、页面和状态设计
- 安全、隐私与学术诚信要求
- 测试、部署、监控和降级策略
- 开发排期与阶段验收标准
- 比赛交付物和最终完成定义

本文不是不可修改的最终规范。实施前应先确认“待确认事项”，并根据实际开发进度控制范围。

## 2. 产品定义

### 2.1 一句话定位

科研小助理是一款面向大一新生的科研启蒙与成长智能体，通过认知测评、个性化学习路线、可信科研知识、实验室与导师公开资料、论文训练和科研简历，帮助学生完成从“不知道科研是什么”到“能够采取第一个科研行动”的过程。

### 2.2 目标用户

首要用户：

- 刚进入大学、不了解科研的大一学生
- 想参加科研但不知道如何开始的本科生
- 不清楚论文、期刊、会议、实验室和导师概念的学生
- 需要规划科研学习路线、准备联系导师材料的学生

比赛 MVP 暂不重点服务：

- 已具备成熟科研经历的研究生
- 需要自动完成正式论文的用户
- 需要导师匿名评价和考研“黑榜”的用户
- 需要完整科研项目管理系统的实验室

### 2.3 产品目标

MVP 必须让用户完成以下闭环：

```text
科研认知测评
    ↓
生成个人科研画像
    ↓
生成阶段性学习路线
    ↓
查询可信科研知识和校内公开资源
    ↓
完成至少一项论文或科研训练任务
    ↓
保存进度并生成下一步建议
```

加分闭环：

```text
成长记录
    ↓
生成科研简历
    ↓
生成联系导师邮件草稿
    ↓
用户核对和修改
```

### 2.4 非目标

第一版不实现：

- 自动代写正式论文
- 自动生成或伪造实验数据
- 自动向导师发送邮件
- 对导师进行主观、人身或未经证实的负面评价
- 自动抓取全校全部教师和实验室
- 多 Agent 自主协作系统
- 大规模论文 PDF 批量解析
- 知识图谱可视化
- 复杂推荐算法和模型训练
- PostgreSQL、pgvector 或独立向量数据库
- 与 Web 主线同时开发完整专家包或 Skill 市场分发

## 3. 赛事交付约束

根据赛事手册，最终作品至少需要：

1. 可直接访问的在线作品链接
2. 3 分钟作品 Demo 视频
3. 作品介绍 PPT
4. GitHub 或 Gitee 源代码仓库
5. LearnBuddy 使用记录

Web 产品必须可在浏览器中独立运行。评委不应依赖本地安装、开发环境或团队现场操作才能体验核心流程。

### 3.1 赛事问题最新口径

以下答复来自现阶段沟通结果。除“Skill 包为可选项”外，其余答复均不是明确许可，不得扩张解释。

| 问题 | 当前答复 | 项目处理 |
|---|---|---|
| Web 运行时是否建议使用 CloudBase AI、混元、DeepSeek或其他模型接口 | 建议不用 | 提交版默认关闭实时外部模型，核心流程不得依赖它 |
| “最终效果最好不要包含第三方 AI”是强制要求还是建议 | 建议不用 | 按审慎口径执行：默认不展示第三方模型，不把第三方模型作为必需链路 |
| LearnBuddy 是否提供适合 Web 调用的正式 API | 不知道，但不建议依赖 | 不等待、不假设存在，也不以其作为当前 Web 架构前提 |
| CodeBuddy CLI 或 Agent SDK 是否属于平台内认可能力 | 不知道 | 仅保留技术验证，不接入提交版主链路，除非后续获得明确答复 |
| 提交页面中的 Skill 包是否必须 | 可选项 | 降为 P2 补充材料，Web 完成后有余力再制作 |
| 方向二是否等同于手册中“需开源”的“赛道二” | 不知道 | 继续按可开源标准准备仓库和许可证，避免最后被动返工 |

### 3.2 对架构的直接影响

- 提交版默认采用“确定性业务流程 + 规则引擎 + 已核验资料检索”。
- 实时模型是可选增强能力，默认关闭，不得成为测评、画像、路线、检索和进度保存的单点依赖。
- AI Provider 接口继续保留，用于开发验证和未来切换，但生产默认值设为 `disabled`。
- “Agent”在第一版中实现为受控任务编排器：根据页面场景或轻量意图规则调用白名单工具，而不是必须依赖大模型自主决策。
- LearnBuddy 的核心评分证据来自需求分析、内容设计、编码、调试、测试和复盘的全过程记录。

## 4. 技术选型

### 4.1 推荐技术栈

| 层级 | 技术选择 | 用途 |
|---|---|---|
| 前端框架 | React + Vite + TypeScript | 构建单页 Web 应用 |
| UI | Tailwind CSS + shadcn/ui | 快速构建一致、可复用的界面 |
| 路由 | React Router | 页面和路由管理 |
| 服务端状态 | TanStack Query | API 请求、缓存、重试和加载状态 |
| 本地状态 | Zustand | 测评过程、当前用户和轻量界面状态 |
| 表单 | React Hook Form + Zod | 表单状态与前后端数据校验 |
| 后端 | CloudBase HTTP 云函数 + Node.js + TypeScript | REST API、任务编排、规则引擎和权限校验 |
| 后端框架 | Express 或轻量路由器 | 在单个 HTTP 云函数内组织接口 |
| 数据库 | CloudBase 文档型数据库 | 用户、测评、计划、资料和成长记录 |
| 身份认证 | CloudBase Auth | 匿名体验和后续账号绑定 |
| AI | 可选 CloudBase AI 或其他合规 Provider，默认关闭 | 仅作增强或技术验证，不承载核心流程 |
| 文件存储 | CloudBase 云存储 | 必要的导出文件和用户附件 |
| 部署 | CloudBase 静态网站托管 + 云函数 | 国内在线访问和 Serverless 后端 |
| 代码托管 | GitHub 或 Gitee | 赛事源码交付与版本管理 |

### 4.2 选型理由

- 从零开始，CloudBase 能集中提供登录、数据库、云函数、存储、AI 和部署，减少平台数量。
- 产品是登录后的交互型 SPA，不依赖 SEO 和服务端页面渲染，因此无需 Next.js SSR。
- 文档数据库足以承载比赛规模的用户画像、学习计划和资料记录。
- 国内访问稳定性对比赛在线体验比复杂架构更重要。
- 受控任务编排器加工具调用已能形成完整智能流程，不需要多 Agent。
- 模型适配器允许在获得明确许可后启用赛事认可的运行时，而不重写产品。
- 核心体验在 `AI_PROVIDER=disabled` 时仍须完整可用。

### 4.3 明确不采用的组合

当前不采用 Next.js + Vercel + PostgreSQL 作为主方案，原因包括：

- Vercel 在中国大陆的访问存在额外风险
- Serverless PostgreSQL 需要连接池和跨区域延迟管理
- Agent SDK、CLI 打包和函数体积会增加交付风险
- 当前产品并不依赖 SSR、复杂关系查询或向量检索
- 组件数量更多，不利于短期比赛开发

如果后续 CloudBase 出现无法解决的阻塞，再通过技术验证决定是否切换，不提前维护双后端。

## 5. 总体架构

```text
┌────────────────────────────────────────────┐
│                React Web                  │
│  测评 / 画像 / 路线 / 问答 / 资源 / 简历  │
└──────────────────────┬─────────────────────┘
                       │ HTTPS / JSON / SSE
                       ▼
┌────────────────────────────────────────────┐
│       CloudBase HTTP Function API          │
│                                            │
│  Auth → Validation → Service → Repository  │
│                         │                  │
│        Workflow Orchestrator + Rules        │
│                         │                  │
│        ┌────────────────┴────────────┐      │
│        │ Optional LLM Provider      │      │
│        │ Tool Registry              │      │
│        │ Prompt and Schema          │      │
│        └─────────────────────────────┘      │
└───────────────┬──────────────┬─────────────┘
                │              │
                ▼              ▼
     CloudBase Database   Optional AI
                │
                ▼
       CloudBase Storage
```

### 5.1 架构原则

1. 前端不直接持有模型密钥或系统提示词。
2. 业务逻辑和数据库操作由后端统一控制；可选模型调用也只能通过后端。
3. Agent 只能访问白名单工具，不能执行任意命令或读写任意文件。
4. 公开资料必须带来源，不允许模型自行生成导师事实。
5. 可确定的逻辑全部使用普通代码；语言生成属于可关闭增强，不影响核心任务完成。
6. 规则结果和可选模型输出都必须经过 Schema 校验后才能写入数据库。
7. 所有核心流程都要有无需模型的降级结果，保证 Demo 不因模型暂时失败而中断。

## 9. 核心业务流程

### 9.1 首次进入与匿名登录

1. 前端初始化 CloudBase SDK。
2. 检查当前登录状态。
3. 未登录时创建匿名身份。
4. 调用 `/api/me/bootstrap`。
5. 后端通过认证信息查找用户；不存在则创建 `users`。
6. 返回用户和 `onboardingCompleted`。
7. 未完成引导则进入测评页；已完成则进入首页。

降级：认证失败时允许进入只读 Demo 模式，但不保存个人数据。

### 9.2 科研认知测评

1. 获取启用的题目。
2. 用户逐题回答；本地保存未提交草稿。
3. 提交后后端校验题目和选项是否合法。
4. 普通代码先计算基础分和标签。
5. 规则引擎使用模板生成易理解的画像描述。
6. 若运行时 AI 已获许可且功能开关开启，可生成增强描述，并使用 Zod 校验。
7. 写入 `assessmentSessions` 和 `researchProfiles`。
8. 返回科研画像和推荐动作。

关键原则：

- 评分逻辑不能完全依赖模型
- 模型关闭或失败时仍返回完整的基础规则结果
- 画像使用成长性语言，避免给用户贴负面标签

### 9.3 学习路线生成

输入：科研画像、专业、兴趣、目标、可投入时间。

处理：

1. 后端读取用户最新画像。
2. 查询匹配的知识条目和资源。
3. 规则引擎根据阶段模板、时间预算和资源标签生成结构化任务列表。
4. 若运行时 AI 已获许可且开启，可在不改变事实资源的前提下润色和个性化任务描述。
5. 无效资源 ID 被删除或替换。
6. 保存计划并返回。

输出至少包含：

- 总目标
- 计划周期
- 每个任务的目的
- 预计完成时间
- 关联学习资料
- 可验证的完成标准

### 9.4 科研知识问答

1. 判断问题属于科研概念、论文、比赛、实验室、导师或学习计划。
2. 优先从已核验知识条目检索候选内容。
3. 将资料及来源传给模型。
4. 默认使用知识条目摘要和模板组织回答；若启用模型，只允许根据给定资料改写。
5. 所有回答返回 `sourceIds`。
6. 前端显示“参考来源”。

如果检索不到可靠资料：

- 明确说明未找到已核验资料
- 可以给出一般性建议
- 不得编造导师、实验室或比赛事实

### 9.5 实验室和导师检索

检索条件：

- 学院
- 专业
- 研究方向
- 兴趣关键词
- 实验室名称

第一版采用字段筛选、标签匹配和简单文本匹配：

```text
匹配得分 = 研究方向命中 + 专业命中 + 兴趣标签命中 + 学院命中
```

若后续获准启用模型，模型只负责：

- 解释为什么匹配
- 将公开简介改写成适合新生阅读的文字
- 建议用户进一步确认的问题

无论是否启用模型，系统都不得：

- 发明导师研究方向
- 判断导师人品
- 生成未经证实的招生承诺

### 9.6 论文训练

比赛 MVP 建议只实现以下一种或两种能力，并优先采用引导模板和检查清单：

- 论文结构识别练习
- 摘要拆解与反馈
- 研究问题和提纲检查
- 文献阅读卡片

不实现“一键生成完整论文”。

若启用模型，其输出必须区分：

- 用户原文
- 修改建议
- 示例表达
- 需要用户自行核验的事实

### 9.7 科研简历与联系导师材料

输入来自用户科研档案和成长记录，不允许系统或模型虚构经历。

生成内容：

- 科研简历草稿
- 能力摘要
- 项目经历表达建议
- 联系导师邮件草稿
- 面谈自我介绍
- 联系前检查清单

输出后必须显示：

> 请核对经历、时间、成果和联系方式。系统不会自动发送邮件。

## 10. API 设计

### 10.1 统一响应结构

成功：

```json
{
  "success": true,
  "data": {},
  "requestId": "req_xxx"
}
```

失败：

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "提交内容不完整",
    "retryable": false
  },
  "requestId": "req_xxx"
}
```

前端只显示适合用户理解的信息；详细错误写入脱敏日志。

### 10.2 建议接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/health` | 健康检查，不依赖模型 |
| GET | `/api/health/ai` | 可选 AI 连通性检查；仅在启用后开放并限制频率 |
| POST | `/api/me/bootstrap` | 初始化匿名用户 |
| GET | `/api/me` | 获取当前用户和科研档案 |
| PATCH | `/api/me/profile` | 更新专业、兴趣和目标 |
| GET | `/api/assessments/questions` | 获取测评题目 |
| POST | `/api/assessments/submit` | 提交测评并生成画像 |
| GET | `/api/assessments/latest` | 获取最新测评 |
| POST | `/api/plans/generate` | 生成学习路线 |
| GET | `/api/plans/current` | 获取当前路线 |
| PATCH | `/api/plans/:planId/tasks/:taskId` | 更新任务状态 |
| GET | `/api/knowledge/search` | 检索科研知识 |
| GET | `/api/labs` | 检索实验室 |
| GET | `/api/labs/:id` | 实验室详情 |
| GET | `/api/mentors` | 检索导师公开资料 |
| GET | `/api/mentors/:id` | 导师公开详情 |
| GET | `/api/competitions` | 检索比赛 |
| POST | `/api/assistant/run` | 受控任务编排；根据场景调用白名单工具 |
| POST | `/api/agent/chat` | 可选实时 Agent 对话；默认关闭 |
| POST | `/api/paper-coach/review` | 论文训练反馈 |
| POST | `/api/resume/generate` | 生成科研简历草稿 |
| GET | `/api/sources/:id` | 获取来源详情 |

### 10.3 接口中间件顺序

```text
Request ID
  ↓
CORS 与安全头
  ↓
认证
  ↓
速率限制
  ↓
Zod 输入校验
  ↓
业务服务
  ↓
统一响应和错误处理
```

### 10.4 超时与重试

- 普通数据库接口目标：3 秒内返回
- 可选模型调用目标：25 秒内返回
- 启用模型时必须设置超时
- 只对网络错误、限流和服务暂时不可用进行最多 1 次重试
- 用户输入错误、权限错误和 Schema 错误不得重试
- Agent 工具调用最多 4 步，防止循环

## 11. AI Provider 设计

### 11.1 统一接口

```ts
export interface LLMProvider {
  generate<T>(input: GenerateInput<T>): Promise<GenerateResult<T>>;
  stream?(input: StreamInput): AsyncIterable<StreamEvent>;
  healthCheck(): Promise<ProviderHealth>;
}
```

实现：

```text
DisabledProvider    提交版默认实现，拒绝实时模型调用
CloudBaseProvider   获得许可后的可选实现
HttpProvider        兼容赛事允许的其他模型端点
MockProvider        本地开发和自动测试
```

### 11.2 Provider 选择

```text
AI_PROVIDER=disabled  → DisabledProvider
AI_PROVIDER=cloudbase → CloudBaseProvider
AI_PROVIDER=http      → HttpProvider
AI_PROVIDER=mock      → MockProvider
```

Provider 切换不能影响：

- API 路径
- 前端组件
- 数据库结构
- Agent 工具 Schema
- 业务服务接口

### 11.3 模型输出规范

所有写入数据库的结果都必须是结构化数据。规则引擎和可选模型共用同一 Schema。例如科研画像：

```ts
const ProfileAnalysisSchema = z.object({
  level: z.string().min(1).max(30),
  summary: z.string().min(20).max(500),
  strengths: z.array(z.string()).max(5),
  gaps: z.array(z.string()).max(5),
  recommendedActions: z.array(z.string()).min(1).max(6),
});
```

如果启用模型后输出无法通过校验：

1. 尝试一次格式修复
2. 再次失败则使用规则生成的降级结果
3. 记录错误类型，不记录敏感内容

## 12. 任务编排器与可选 Agent 设计

### 12.1 默认实现：受控任务编排器

提交版默认运行 `research_assistant` 任务编排器。它使用页面场景、按钮动作和轻量意图规则选择工具，不要求实时大模型参与。

职责：

- 根据明确场景或规则判断用户任务
- 读取用户科研档案
- 调用白名单工具并组合模板化结果
- 基于已核验资料回答事实问题
- 根据科研画像和任务状态给出下一步行动
- 保存必要的成长记录

不具备：

- 任意代码执行
- 任意文件读取
- 任意网页访问
- 自动发送邮件
- 修改导师或实验室资料
- 对用户作医学、心理或人格诊断

如果后续获得明确许可，可在相同工具接口上启用 LLM Agent，由模型辅助选择工具和组织自然语言；核心数据和权限逻辑不变。

### 12.2 工具清单

| 工具 | 输入 | 输出 |
|---|---|---|
| `get_user_profile` | `userId` | 科研画像 |
| `search_knowledge` | 查询词、分类 | 知识条目和来源 |
| `search_labs` | 专业、方向、关键词 | 实验室列表 |
| `search_mentors` | 学院、方向、关键词 | 导师公开资料 |
| `search_competitions` | 专业、兴趣、时间 | 比赛列表 |
| `get_learning_plan` | `userId` | 当前路线和进度 |
| `save_learning_plan` | 结构化计划 | 保存结果 |
| `update_task_progress` | 计划和任务 ID | 更新结果 |
| `get_resume_facts` | `userId` | 可用于简历的真实事实 |

所有工具均由后端代码实现。任务编排器或可选模型只能传入参数和读取返回结果，不能直接操作数据库。

### 12.3 默认执行循环

```text
接收页面场景或用户动作
  ↓
加载最小必要用户上下文
  ↓
规则路由选择白名单工具
  ↓
校验工具名和参数
  ↓
执行工具并返回结果
  ↓
按预定义流程最多继续 3 次工具调用
  ↓
模板生成最终结果和来源列表
  ↓
保存脱敏会话记录
```

启用可选 LLM Agent 后，仅将“规则路由”和“模板生成”替换为模型辅助决策，工具、校验、循环上限和来源规则保持不变。

### 12.4 可选 Prompt 分层

```text
系统层：身份、职责、安全边界、事实规则
场景层：测评、路线、检索、论文训练或简历
用户层：用户问题
上下文层：科研画像、工具结果、来源资料
输出层：JSON Schema 或回答格式
```

可选 AI 启用时，Prompt 文件必须包含版本号，例如：

```text
content/prompts/research-assistant/v1.md
content/prompts/assessment-analysis/v1.md
content/prompts/learning-plan/v1.md
```

数据库保存 `promptVersion`，方便说明模型行为如何迭代。

### 12.5 事实回答规则

涉及以下内容时，无论由模板还是模型回答，都必须使用来源：

- 导师研究方向和公开简介
- 实验室信息
- 学校、学院和机构信息
- 科研比赛信息
- 论文和期刊事实

找不到可靠来源时，必须回答“当前资料库中没有足够的已核验信息”，而不是猜测。

### 14.2 Dashboard

首页优先显示：

- 当前科研阶段
- 今日或下一项任务
- 学习路线完成度
- 最近保存的兴趣方向
- 推荐的实验室或学习资料
- “继续上次进度”按钮

不要把首页做成纯聊天界面。成长状态和明确行动应比聊天输入框更突出。

### 14.3 测评页面

- 每次只显示一题或一小组题
- 显示进度
- 所有题目支持“不了解”选项
- 支持返回修改
- 提交前进行完整性检查
- 生成画像期间显示明确进度状态

### 14.4 加载、空状态和错误状态

所有核心页面必须具备：

- Skeleton 或加载提示
- 空数据说明和下一步按钮
- 可重试错误状态
- 模型超时的降级结果
- 无权限或登录失效提示

禁止出现：

- 无限转圈
- 空白页面
- 直接展示后端堆栈
- 按钮点击后没有反馈

### 14.5 Demo 模式

提供稳定的演示入口：

- 自动创建 Demo 用户
- 预置一份计算机大一新生科研画像
- 预置一条可展示的学习路线
- 预置若干已核验实验室和导师资料
- 生产默认使用规则和模板结果；若可选模型不可用，不影响演示

Demo 模式只用于确保演示稳定，不得将预置或模板结果伪装成实时模型生成结果。

## 15. 安全、隐私和学术诚信

### 15.1 身份与权限

- 后端从可信认证上下文获取用户身份，不接受前端自报 `userId`
- 用户只能读取和修改自己的画像、计划和会话
- 公开资料仅允许管理员或导入脚本修改
- 健康检查不得泄露配置和密钥

### 15.2 输入安全

- 所有输入通过 Zod 校验
- 对长文本设置长度上限
- 富文本输出进行安全渲染
- 不执行模型返回的 HTML、JavaScript 或命令
- Agent 工具参数必须再次校验

### 15.3 速率与费用保护

- 匿名用户限制每分钟调用次数
- 若启用 AI，为其设置单用户日限额
- 相同请求短时间内可缓存
- 超限时返回明确提示
- AI 始终可通过开关关闭，且关闭后资料检索、测评、画像、路线和进度功能仍完整可用

### 15.4 个人数据

MVP 尽量少收集：

- 不要求真实姓名
- 不要求学号
- 不要求手机号
- 不收集身份证等敏感信息
- 联系导师邮件中的个人信息由用户自行填写和确认

应提供：

- 隐私说明
- 清除个人成长记录的入口
- 匿名模式说明

### 15.5 学术诚信

论文训练模块必须明确：

- 不代写正式提交论文
- 不伪造引用、实验和数据
- 不承诺论文发表
- AI 输出需要用户核验
- 生成示例不得冒充用户真实成果

## 16. 错误处理、日志和可观测性

### 16.1 错误分类

```text
VALIDATION_ERROR       输入不合法
UNAUTHORIZED           未登录或身份失效
FORBIDDEN              无权限
NOT_FOUND              资源不存在
RATE_LIMITED           请求过多
AI_TIMEOUT             模型超时
AI_OUTPUT_INVALID      模型结构化输出无效
DEPENDENCY_UNAVAILABLE 外部服务不可用
INTERNAL_ERROR         未知服务端错误
```

### 16.2 结构化日志

每条日志建议包含：

```json
{
  "requestId": "req_xxx",
  "route": "/api/plans/generate",
  "userHash": "hash_xxx",
  "durationMs": 1234,
  "status": 200,
  "aiProvider": "cloudbase",
  "toolSteps": 2,
  "errorCode": null
}
```

禁止记录：

- 完整认证 Token
- 模型 API Key
- 腾讯云 SecretKey
- 用户完整简历和邮件内容
- 未脱敏的私人联系方式

### 16.3 健康检查

`/api/health` 检查：

- 后端是否启动
- 数据库能否完成轻量查询
- 当前版本和环境

启用可选 AI 时，`/api/health/ai` 检查：

- Provider 是否配置
- 是否能完成最小模型调用
- 最近错误状态

AI 健康接口应限制频率，不能公开模型密钥或详细内部信息。

## 17. 测试策略

### 17.1 单元测试

优先覆盖：

- 测评分数计算
- 画像规则降级逻辑
- 学习计划 Schema
- 匹配得分计算
- 来源引用去重
- Provider 选择逻辑
- Agent 工具参数校验
- 权限判断

### 17.2 集成测试

使用规则引擎和 MockProvider 分别测试：

- 测评提交后生成画像并入库
- 根据画像生成学习计划
- 搜索实验室并返回来源
- 任务编排器调用工具后生成最终结果
- 可选模型输出无效时触发规则降级
- 用户不能读取其他用户数据

### 17.3 端到端测试

至少覆盖以下路径：

```text
匿名登录
  → 完成测评
  → 查看画像
  → 生成路线
  → 完成一个任务
  → 搜索实验室
  → 运行科研助理任务并查看来源
```

### 17.4 人工验收

- 手机和电脑浏览器分别测试
- 校园网、家庭网络和手机流量分别测试
- 由未参与开发的同学完整体验

- 检查 Demo 视频路线是否稳定
- 在 AI 临时不可用时验证降级体验

## 18. 部署流程

### 18.1 环境划分

至少使用：

- `development`：本地开发和测试数据
- `production`：评委体验环境

如果资源允许，可增加 `preview` 供队员验收。

严禁开发脚本直接清空生产数据库。

### 18.2 部署步骤

```text
安装依赖并锁定 lockfile
  ↓
Lint + Type Check + Unit Test
  ↓
构建前端
  ↓
部署云函数
  ↓
运行数据库初始化和内容导入
  ↓
部署静态网站
  ↓
运行健康检查
  ↓
运行核心 E2E 测试
  ↓
手机流量测试在线地址
```

### 18.3 发布前检查

- 在线地址可以直接打开
- HTTPS 正常
- 匿名登录正常
- 核心 API 正常
- 默认无 AI 模式正常；若启用 AI，其调用和关闭降级均正常
- 数据库权限正确
- 生产环境没有测试密钥和敏感日志
- 来源链接可以点击
- Demo 账号和 Demo 数据可用
- GitHub/Gitee 仓库 README 完整
- 第三方依赖和许可证已注明

## 22. 最终完成定义

只有同时满足以下条件，Web 主作品才算完成：

- 评委通过在线链接可以打开产品
- 无需团队协助即可开始体验
- 用户能够完成测评并获得科研画像
- 用户能够生成并保存学习路线
- 用户可以查询至少一类带来源的真实科研资源
- 任务编排器能够调用工具并使用用户档案，而不是只进行无上下文闲聊
- 页面明确区分公开事实、AI 建议和待核验信息
- 默认关闭实时模型；若后续获准启用，关闭或调用失败时仍能回到规则结果
- 用户数据不会被其他用户读取
- 仓库不存在真实密钥
- README 能说明本地运行、部署、数据来源和团队分工
- 生产环境经过电脑端和手机流量测试
- Demo 视频中的操作路径与线上版本一致
- LearnBuddy 使用记录覆盖需求、设计、编码、调试、测试和复盘

## 23. 实施 Agent 工作规则

后续将本文交给开发 Agent 时，应同时附带以下要求：

1. 先检查仓库现状，不假设项目尚未初始化。
2. 每次只实现一个可验收阶段，不同时铺开全部功能。
3. 修改前说明本阶段目标、文件范围和验收方式。
4. 所有数据库写入先通过 Zod 校验。
5. 提交版默认 `AI_PROVIDER=disabled`；任何获准启用的模型调用必须经过 `LLMProvider`。
6. 所有事实型公开资料必须带 `sourceIds`。
7. 不在获得明确许可前把实时模型或 Agent SDK 接入提交版主链路。
8. 不擅自加入多 Agent、向量数据库、自动爬虫和论文代写。
9. 每个阶段结束运行类型检查、测试和构建。
10. 发现文档与实际平台能力冲突时，先做最小技术验证并记录结果，再修改方案。
