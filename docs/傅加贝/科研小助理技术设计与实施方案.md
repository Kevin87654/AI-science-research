## 2. 产品定义

### 2.1 一句话定位

科研小助理是一款面向大一新生的科研启蒙与成长智能体，通过认知测评、个性化学习路线、可信科研知识、实验室与导师公开资料、论文训练和科研简历，帮助学生完成从“不知道科研是什么”到“能够采取第一个科研行动”的过程。

### 2.2 目标用户

首要用户：

- 刚进入大学、不了解科研的大一学生
- 想参加科研但不知道如何开始的本科生
- 不清楚论文、期刊、会议、实验室和导师概念的学生
- 需要规划科研学习路线、准备联系导师材料的学生

比赛 MVP 暂不重点服务：

- 已具备成熟科研经历的研究生
- 需要自动完成正式论文的用户
- 需要导师匿名评价和考研“黑榜”的用户
- 需要完整科研项目管理系统的实验室

### 2.3 产品目标

MVP 必须让用户完成以下闭环：

```text
科研认知测评
    ↓
生成个人科研画像
    ↓
生成阶段性学习路线
    ↓
查询可信科研知识和校内公开资源
    ↓
完成至少一项论文或科研训练任务
    ↓
保存进度并生成下一步建议
```

加分闭环：

```text
成长记录
    ↓
生成科研简历
    ↓
生成联系导师邮件草稿
    ↓
用户核对和修改
```

### 2.4 非目标

第一版不实现：

- 自动代写正式论文
- 自动生成或伪造实验数据
- 自动向导师发送邮件
- 对导师进行主观、人身或未经证实的负面评价
- 自动抓取全校全部教师和实验室
- 多 Agent 自主协作系统
- 大规模论文 PDF 批量解析
- 知识图谱可视化
- 复杂推荐算法和模型训练
- 独立向量数据库；pgvector 仅作为后续可选能力
- 与 Web 主线同时开发完整专家包或 Skill 市场分发

## 3. 赛事交付约束

根据赛事手册，最终作品至少需要：

1. 可直接访问的在线作品链接
2. 3 分钟作品 Demo 视频
3. 作品介绍 PPT
4. GitHub 或 Gitee 源代码仓库
5. LearnBuddy 使用记录

Web 产品必须可在浏览器中独立运行。评委不应依赖本地安装、开发环境或团队现场操作才能体验核心流程。

### 3.1 赛事问题最新口径

以下答复来自现阶段沟通结果。除“Skill 包为可选项”外，其余答复均不是明确许可，不得扩张解释。

| 问题 | 当前答复 | 项目处理 |
|---|---|---|
| Web 运行时是否建议使用 CloudBase AI、混元、DeepSeek或其他模型接口 | 建议不用 | 提交版默认关闭实时外部模型，核心流程不得依赖它 |
| “最终效果最好不要包含第三方 AI”是强制要求还是建议 | 建议不用 | 按审慎口径执行：默认不展示第三方模型，不把第三方模型作为必需链路 |
| LearnBuddy 是否提供适合 Web 调用的正式 API | 不知道，但不建议依赖 | 不等待、不假设存在，也不以其作为当前 Web 架构前提 |
| CodeBuddy CLI 或 Agent SDK 是否属于平台内认可能力 | 不知道 | 仅保留技术验证，不接入提交版主链路，除非后续获得明确答复 |
| 提交页面中的 Skill 包是否必须 | 可选项 | 降为 P2 补充材料，Web 完成后有余力再制作 |
| 方向二是否等同于手册中“需开源”的“赛道二” | 不知道 | 继续按可开源标准准备仓库和许可证，避免最后被动返工 |

### 3.2 对架构的直接影响

- 提交版默认采用“确定性业务流程 + 规则引擎 + 已核验资料检索”。
- 实时模型是可选增强能力，默认关闭，不得成为测评、画像、路线、检索和进度保存的单点依赖。
- AI Provider 接口继续保留，用于开发验证和未来切换，但生产默认值设为 `disabled`。
- “Agent”在第一版中实现为受控任务编排器：根据页面场景或轻量意图规则调用白名单工具，而不是必须依赖大模型自主决策。
- LearnBuddy 的核心评分证据来自需求分析、内容设计、编码、调试、测试和复盘的全过程记录。

## 4. 技术选型

### 4.1 推荐技术栈

| 层级 | 技术选择 | 用途 |
|---|---|---|
| 全栈框架 | Next.js App Router + TypeScript | 页面、Route Handlers 与服务端业务逻辑 |
| UI | Tailwind CSS + shadcn/ui | 快速构建一致、可复用的界面 |
| 客户端状态 | React 状态；复杂交互再引入 Zustand | 测评草稿和轻量界面状态 |
| 表单 | React Hook Form + Zod | 表单状态与前后端数据校验 |
| 后端 | Next.js Route Handlers，部署为 Vercel Functions | API、匿名会话、任务编排、规则引擎和权限校验 |
| 部署区域 | Vercel `hkg1` | 缩短深圳用户和上海数据库之间的链路 |
| 数据库 | CloudBase PostgreSQL 17，通过 PostgREST/HTTP 网关访问 | 用户、测评、计划、资料和成长记录 |
| 数据访问 | Repository 适配器 + 原生 `fetch` | 隔离 PostgREST，方便未来更换数据库 |
| 身份认证 | Vercel 服务端匿名会话方案 A | HttpOnly Cookie + 数据库存储会话哈希 |
| AI | 可选 Provider，默认关闭 | 仅作增强或技术验证，不承载核心流程 |
| 文件存储 | P0 不引入；必要导出优先浏览器生成 | 避免增加第三个平台和上传链路 |
| 部署 | Vercel Git 自动部署 | 主体 Web、预览环境和生产链接 |
| 代码托管 | GitHub 或 Gitee | 赛事源码交付与版本管理 |

### 4.2 选型理由

- 组委会已明确 Vercel 可以用于作品链接，因此不再把 Vercel 合规性视为阻塞项。
- Next.js 与 Vercel 的部署、预览、Route Handler 和日志链路较成熟，适合短期迭代。
- CloudBase PostgreSQL 的 HTTP CRUD 与 pgvector 已被组员实测跑通，无须新增 Neon 或 Supabase。
- PostgREST 使用无状态 HTTPS，不需要 Serverless PostgreSQL 连接池。
- 前端、会话和业务 API 均在 Vercel 同源，浏览器不会直接持有 CloudBase 管理级 API Key。
- 匿名会话方案 A 不依赖 CloudBase Auth，评委打开即可体验。
- 受控任务编排器加工具调用已能形成完整智能流程，不需要多 Agent。
- 模型适配器允许在获得明确许可后启用赛事认可的运行时，而不重写产品。
- 核心体验在 `AI_PROVIDER=disabled` 时仍须完整可用。

### 4.3 当前明确不采用的组合

当前不采用“全部放在 CloudBase”的方案，原因包括：

- CloudBase 默认静态托管域名存在提示中间页和正式使用限制
- 自定义域名可能涉及 ICP 备案
- 免费云函数运行 CodeBuddy CLI 实测约 35 秒且内存余量较小
- HTTP 型云函数需要额外 `scf_bootstrap` 和端口启动配置
- Vercel 主体的 Git 自动部署与预览环境更适合比赛迭代

同时不新增 Neon/Supabase，也不维护 Vercel 与 CloudBase 两套应用主体。CloudBase 当前仅作为 PostgreSQL 数据服务和管控面。

## 5. 总体架构

```text
┌────────────────────────────────────────────┐
│       Next.js Web on Vercel               │
│  测评 / 画像 / 路线 / 问答 / 资源 / 简历  │
└──────────────────────┬─────────────────────┘
                       │ Same-origin HTTPS
                       ▼
┌────────────────────────────────────────────┐
│  Next.js Route Handlers / Vercel hkg1      │
│                                            │
│ Session → CSRF → Validation → Service      │
│                         │                  │
│        Workflow Orchestrator + Rules        │
│                         │                  │
│        ┌────────────────┴────────────┐      │
│        │ Optional LLM Provider      │      │
│        │ Tool Registry              │      │
│        │ CloudBase Repository       │      │
│        └─────────────────────────────┘      │
└───────────────┬──────────────┬─────────────┘
                │ HTTPS        │ Optional
                ▼              ▼
 CloudBase PostgREST       Allowed AI Provider
                │
                ▼
 CloudBase PostgreSQL 17
```

### 5.1 架构原则

1. 浏览器不直接持有 CloudBase API Key、模型密钥或系统提示词。
2. 数据库和可选模型调用只能从 Vercel 服务端发起。
3. Agent 只能访问白名单工具，不能执行任意命令或读写任意文件。
4. 公开资料必须带来源，不允许模型自行生成导师事实。
5. 可确定的逻辑全部使用普通代码；语言生成属于可关闭增强，不影响核心任务完成。
6. 规则结果和可选模型输出都必须经过 Schema 校验后才能写入数据库。
7. 所有核心流程都要有无需模型的降级结果，保证 Demo 不因模型暂时失败而中断。
8. 数据访问必须经过 Repository，不允许页面或 Route Handler 散落 PostgREST URL。
9. 前端传入的 `userId` 永远不可信，用户身份只能来自服务端会话。

## 7. 环境与配置

### 7.1 浏览器可见配置

```env
NEXT_PUBLIC_APP_ENV=development
NEXT_PUBLIC_ENABLE_DEMO_MODE=true
```

仅允许放置可公开信息，不得使用 `NEXT_PUBLIC_` 暴露 CloudBase API Key、会话密钥或模型密钥。

### 7.2 后端私密配置

```env
APP_ENV=development
CLOUDBASE_PG_REST_BASE_URL=
CLOUDBASE_PG_API_KEY=
SESSION_SECRET=
SESSION_COOKIE_NAME=research_session
SESSION_TTL_SECONDS=604800
AI_PROVIDER=disabled
AI_MODEL=
AI_REQUEST_TIMEOUT_MS=25000
AI_MAX_TOOL_STEPS=4
ENABLE_RUNTIME_AI=false
ENABLE_STREAMING=false
ENABLE_DEMO_FALLBACK=true
LOG_LEVEL=info
```

如果后续使用兼容接口：

```env
HTTP_LLM_BASE_URL=
HTTP_LLM_API_KEY=
HTTP_LLM_MODEL=
```

约束：

- `.env.local` 和真实密钥必须加入 `.gitignore`
- 仓库只提交 `.env.example`
- 日志禁止输出完整 Token、Secret、Prompt 中的个人信息
- 不得在前端直接调用 CloudBase PostgREST 或需要私密密钥的模型接口
- Vercel Preview 与 Production 使用不同的 `SESSION_SECRET` 和数据环境
- CloudBase API Key 应定期轮换，泄露后必须立即作废

### 7.3 Vercel Runtime 配置

所有访问 CloudBase 的 Route Handler 使用 Node.js Runtime，并优先运行在香港区域：

```ts
export const runtime = 'nodejs';
export const preferredRegion = 'hkg1';
```

项目部署后必须从日志或探针确认实际函数区域，不能只依赖配置文件存在。数据库请求设置显式超时，并记录 `cloudbaseDurationMs`。

## 8. 数据模型

数据库使用 CloudBase PostgreSQL。SQL 表和列使用 `snake_case`，TypeScript 类型使用 `camelCase`，由 Repository 负责转换。

当前共享实例不能从 Vercel 使用标准 `pg` 协议直连，因此：

- 运行时 CRUD 通过 PostgREST HTTP 网关完成
- 建表、索引、扩展和迁移通过 CloudBase 控制台、CLI 或连接器执行
- 复杂事务和多表操作封装为 PostgreSQL RPC 函数
- Route Handler 不接受用户传入的原始 PostgREST 过滤表达式

所有主要表建议包含：

```ts
type BaseRecord = {
  id: string;
  createdAt: string;
  updatedAt: string;
  schemaVersion: number;
};
```

### 8.1 users

保存匿名用户和基础设置，不保存可由科研档案推导的冗余信息。

```ts
type User = BaseRecord & {
  displayName?: string;
  accountType: 'anonymous' | 'demo';
  onboardingCompleted: boolean;
  privacyAcceptedAt?: string;
  lastActiveAt: string;
};
```

索引：

- `lastActiveAt` 普通索引

### 8.2 sessions

匿名会话采用数据库存储的随机 Token 哈希：

```ts
type Session = BaseRecord & {
  userId: string;
  tokenHash: string;
  expiresAt: string;
  lastSeenAt: string;
  revokedAt?: string;
};
```

要求：

- 浏览器 Cookie 保存原始随机 Token
- 数据库只保存 `SHA-256` 后的 Token 哈希
- `token_hash` 建唯一索引
- `expires_at` 建普通索引，便于定期清理
- 会话 Token 至少使用 256 bit 安全随机数
- Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`
- 生产环境不允许将 `userId` 直接作为身份凭证

### 8.9 mentors

```ts
type Mentor = BaseRecord & {
  name: string;
  school: string;
  college: string;
  title?: string;
  publicBio: string;
  researchAreas: string[];
  labIds: string[];
  homepage?: string;
  publicContact?: string;
  sourceIds: string[];
  verifiedAt: string;
  active: boolean;
};
```

禁止保存或生成：

- 未经本人公开的联系方式
- 身份证、住址、私人手机等敏感信息
- 未经证实的师德、人品或负面评价
- “导师是不是人类”一类侮辱性评分

产品可以计算“方向匹配度”，但必须展示匹配依据，不能将其包装为导师质量评分。

### 8.10 competitions

```ts
type Competition = BaseRecord & {
  name: string;
  organizer: string;
  description: string;
  suitableMajors: string[];
  tags: string[];
  officialUrl: string;
  registrationWindow?: string;
  reviewStatus: 'draft' | 'verified' | 'expired';
  sourceIds: string[];
};
```

### 8.11 sources

```ts
type Source = BaseRecord & {
  title: string;
  url: string;
  publisher: string;
  sourceType: 'official' | 'school' | 'college' | 'lab' | 'paper' | 'other';
  collectedAt: string;
  verifiedAt?: string;
  verifiedBy?: string;
  status: 'pending' | 'verified' | 'invalid';
  note?: string;

```

### 8.12 chatSessions

```ts
type ChatSession = BaseRecord & {
  userId: string;
  title: string;
  scene: 'general' | 'plan' | 'lab-search' | 'paper-coach' | 'resume';
  messages: Array<{
    id: string;
    role: 'user' | 'assistant' | 'tool';
    content: string;
    toolName?: string;
    sourceIds?: string[];
    createdAt: string;
  }>;
};
```

如果单个会话可能过长，应将消息拆分为独立 `chat_messages` 表，避免单行 `jsonb` 无限增长。

### 8.13 PostgreSQL 落表约定

推荐表名：

```text
users
sessions
research_profiles
assessment_questions
assessment_sessions
learning_plans
knowledge_items
labs
mentors
competitions
sources
chat_sessions
```

字段映射：

- TypeScript 的 `createdAt` 对应 SQL 的 `created_at`
- 字符串数组优先使用 `text[]`
- 测评答案、学习任务等可变嵌套结构使用 `jsonb`
- 可搜索的研究方向和标签使用数组并建立 GIN 索引
- 用户私有表均包含 `user_id uuid not null`
- 所有外键建立索引
- 时间字段统一使用 `timestamptz`
- 主键统一使用 UUID

首版不主动使用 pgvector。只有当标签检索无法满足知识检索时，再通过迁移增加向量列和索引。

复杂操作建议封装为 RPC：

```text
create_anonymous_user_and_session
submit_assessment
replace_active_learning_plan
mark_learning_task_done
consume_rate_limit
revoke_session
```

RPC 必须有固定参数、固定返回结构和权限检查，不接受任意 SQL 片段。

## 9. 核心业务流程

### 9.1 首次进入与匿名登录

1. 浏览器访问 Next.js 应用并调用 `/api/session/bootstrap`。
2. Route Handler 检查 HttpOnly 会话 Cookie。
3. Cookie 不存在、无效或已过期时，服务端生成至少 256 bit 随机 Token。
4. 服务端创建匿名 `users` 记录，并将 Token 的 SHA-256 哈希写入 `sessions`。
5. 原始 Token 仅写入 `HttpOnly + Secure + SameSite=Lax` Cookie。
6. 后续请求只从 Cookie 取得 Token，哈希后查询 `sessions`，再得到可信 `userId`。
7. 返回用户和 `onboardingCompleted`，未完成引导则进入测评页。

禁止：

- 在 LocalStorage 保存会话 Token
- 在 URL 中传递会话 Token
- 接受前端传入的 `userId` 作为权限依据
- 将原始 Token 写入数据库或日志

降级：会话服务失败时允许进入只读 Demo 模式，但不保存个人数据。

### 9.2 科研认知测评

1. 获取启用的题目。
2. 用户逐题回答；本地保存未提交草稿。
3. 提交后后端校验题目和选项是否合法。
4. 普通代码先计算基础分和标签。
5. 规则引擎使用模板生成易理解的画像描述。
6. 若运行时 AI 已获许可且功能开关开启，可生成增强描述，并使用 Zod 校验。
7. 写入 `assessmentSessions` 和 `researchProfiles`。
8. 返回科研画像和推荐动作。

关键原则：

- 评分逻辑不能完全依赖模型
- 模型关闭或失败时仍返回完整的基础规则结果
- 画像使用成长性语言，避免给用户贴负面标签

### 9.3 学习路线生成

输入：科研画像、专业、兴趣、目标、可投入时间。

处理：

1. 后端读取用户最新画像。
2. 查询匹配的知识条目和资源。
3. 规则引擎根据阶段模板、时间预算和资源标签生成结构化任务列表。
4. 若运行时 AI 已获许可且开启，可在不改变事实资源的前提下润色和个性化任务描述。
5. 无效资源 ID 被删除或替换。
6. 保存计划并返回。

输出至少包含：

- 总目标
- 计划周期
- 每个任务的目的
- 预计完成时间
- 关联学习资料
- 可验证的完成标准

### 9.4 科研知识问答

1. 判断问题属于科研概念、论文、比赛、实验室、导师或学习计划。
2. 优先从已核验知识条目检索候选内容。
3. 将资料及来源传给模型。
4. 默认使用知识条目摘要和模板组织回答；若启用模型，只允许根据给定资料改写。
5. 所有回答返回 `sourceIds`。
6. 前端显示“参考来源”。

如果检索不到可靠资料：

- 明确说明未找到已核验资料
- 可以给出一般性建议
- 不得编造导师、实验室或比赛事实

### 9.5 实验室和导师检索

检索条件：

- 学院
- 专业
- 研究方向
- 兴趣关键词
- 实验室名称

第一版采用字段筛选、标签匹配和简单文本匹配：

```text
匹配得分 = 研究方向命中 + 专业命中 + 兴趣标签命中 + 学院命中
```

若后续获准启用模型，模型只负责：

- 解释为什么匹配
- 将公开简介改写成适合新生阅读的文字
- 建议用户进一步确认的问题

无论是否启用模型，系统都不得：

- 发明导师研究方向
- 判断导师人品
- 生成未经证实的招生承诺

### 9.6 论文训练

比赛 MVP 建议只实现以下一种或两种能力，并优先采用引导模板和检查清单：

- 论文结构识别练习
- 摘要拆解与反馈
- 研究问题和提纲检查
- 文献阅读卡片

不实现“一键生成完整论文”。

若启用模型，其输出必须区分：

- 用户原文
- 修改建议
- 示例表达
- 需要用户自行核验的事实

### 9.7 科研简历与联系导师材料

输入来自用户科研档案和成长记录，不允许系统或模型虚构经历。

生成内容：

- 科研简历草稿
- 能力摘要
- 项目经历表达建议
- 联系导师邮件草稿
- 面谈自我介绍
- 联系前检查清单

输出后必须显示：

> 请核对经历、时间、成果和联系方式。系统不会自动发送邮件。

## 10. API 设计

### 10.1 统一响应结构

成功：

```json
{
  "success": true,
  "data": {},
  "requestId": "req_xxx"
}
```

失败：

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",

  },
```

前端只显示适合用户理解的信息；详细错误写入脱敏日志。

| GET | `/api/assessments/questions` | 获取测评题目 |
| POST | `/api/assessments/submit` | 提交测评并生成画像 |
| GET | `/api/assessments/latest` | 获取最新测评 |
| POST | `/api/plans/generate` | 生成学习路线 |
| GET | `/api/plans/current` | 获取当前路线 |
| PATCH | `/api/plans/:planId/tasks/:taskId` | 更新任务状态 |
| GET | `/api/knowledge/search` | 检索科研知识 |

| GET | `/api/competitions` | 检索比赛 |
| POST | `/api/assistant/run` | 受控任务编排；根据场景调用白名单工具 |
| POST | `/api/agent/chat` | 可选实时 Agent 对话；默认关闭 |
| POST | `/api/paper-coach/review` | 论文训练反馈 |
| POST | `/api/resume/generate` | 生成科研简历草稿 |
| GET | `/api/sources/:id` | 获取来源详情 |

### 10.3 接口中间件顺序

```text
Request ID
  ↓
同源检查与安全头
  ↓
会话 Cookie 验证
  ↓
变更请求的 Origin/CSRF 检查
  ↓
速率限制
  ↓
Zod 输入校验
  ↓
业务服务
  ↓
统一响应和错误处理
```

### 10.4 超时与重试

- 普通数据库接口目标：3 秒内返回
- 可选模型调用目标：25 秒内返回
- 启用模型时必须设置超时
- 只对网络错误、限流和服务暂时不可用进行最多 1 次重试
- 用户输入错误、权限错误和 Schema 错误不得重试
- Agent 工具调用最多 4 步，防止循环

## 11. AI Provider 设计

### 11.1 统一接口

```ts
export interface LLMProvider {
  generate<T>(input: GenerateInput<T>): Promise<GenerateResult<T>>;
  stream?(input: StreamInput): AsyncIterable<StreamEvent>;
  healthCheck(): Promise<ProviderHealth>;
}
```

实现：

```text
DisabledProvider    提交版默认实现，拒绝实时模型调用
CloudBaseProvider   获得许可后的可选实现
HttpProvider        兼容赛事允许的其他模型端点
MockProvider        本地开发和自动测试
```

### 11.2 Provider 选择

```text
AI_PROVIDER=disabled  → DisabledProvider
AI_PROVIDER=cloudbase → CloudBaseProvider
AI_PROVIDER=http      → HttpProvider
AI_PROVIDER=mock      → MockProvider
```

Provider 切换不能影响：

- API 路径
- 前端组件
- 数据库结构
- Agent 工具 Schema
- 业务服务接口

### 11.3 模型输出规范

所有写入数据库的结果都必须是结构化数据。规则引擎和可选模型共用同一 Schema。例如科研画像：

```ts
const ProfileAnalysisSchema = z.object({
  level: z.string().min(1).max(30),
  summary: z.string().min(20).max(500),
  strengths: z.array(z.string()).max(5),
  gaps: z.array(z.string()).max(5),
  recommendedActions: z.array(z.string()).min(1).max(6),
});
```

如果启用模型后输出无法通过校验：

1. 尝试一次格式修复
2. 再次失败则使用规则生成的降级结果
3. 记录错误类型，不记录敏感内容

## 12. 任务编排器与可选 Agent 设计

### 12.1 默认实现：受控任务编排器

提交版默认运行 `research_assistant` 任务编排器。它使用页面场景、按钮动作和轻量意图规则选择工具，不要求实时大模型参与。

职责：

- 根据明确场景或规则判断用户任务
- 读取用户科研档案
- 调用白名单工具并组合模板化结果
- 基于已核验资料回答事实问题
- 根据科研画像和任务状态给出下一步行动
- 保存必要的成长记录

不具备：

- 任意代码执行
- 任意文件读取
- 任意网页访问
- 自动发送邮件
- 修改导师或实验室资料
- 对用户作医学、心理或人格诊断

如果后续获得明确许可，可在相同工具接口上启用 LLM Agent，由模型辅助选择工具和组织自然语言；核心数据和权限逻辑不变。

### 12.2 工具清单

| 工具 | 输入 | 输出 |
|---|---|---|
| `get_user_profile` | `userId` | 科研画像 |
| `search_knowledge` | 查询词、分类 | 知识条目和来源 |
| `search_labs` | 专业、方向、关键词 | 实验室列表 |
| `search_mentors` | 学院、方向、关键词 | 导师公开资料 |
| `search_competitions` | 专业、兴趣、时间 | 比赛列表 |
| `get_learning_plan` | `userId` | 当前路线和进度 |
| `save_learning_plan` | 结构化计划 | 保存结果 |
| `update_task_progress` | 计划和任务 ID | 更新结果 |
| `get_resume_facts` | `userId` | 可用于简历的真实事实 |

所有工具均由后端代码实现。任务编排器或可选模型只能传入参数和读取返回结果，不能直接操作数据库。

### 12.3 默认执行循环

```text
接收页面场景或用户动作
  ↓
加载最小必要用户上下文
  ↓
规则路由选择白名单工具
  ↓
校验工具名和参数
  ↓
执行工具并返回结果
  ↓
按预定义流程最多继续 3 次工具调用
  ↓
模板生成最终结果和来源列表
  ↓
保存脱敏会话记录
```

启用可选 LLM Agent 后，仅将“规则路由”和“模板生成”替换为模型辅助决策，工具、校验、循环上限和来源规则保持不变。

### 12.4 可选 Prompt 分层

```text
系统层：身份、职责、安全边界、事实规则
场景层：测评、路线、检索、论文训练或简历
用户层：用户问题
上下文层：科研画像、工具结果、来源资料
输出层：JSON Schema 或回答格式
```

可选 AI 启用时，Prompt 文件必须包含版本号，例如：

```text
content/prompts/research-assistant/v1.md
content/prompts/assessment-analysis/v1.md
content/prompts/learning-plan/v1.md
```

数据库保存 `promptVersion`，方便说明模型行为如何迭代。

### 12.5 事实回答规则

涉及以下内容时，无论由模板还是模型回答，都必须使用来源：

- 导师研究方向和公开简介
- 实验室信息
- 学校、学院和机构信息
- 科研比赛信息
- 论文和期刊事实

找不到可靠来源时，必须回答“当前资料库中没有足够的已核验信息”，而不是猜测。

## 15. 安全、隐私和学术诚信

### 15.1 身份与权限

- 后端从 HttpOnly Cookie 和数据库会话获取身份，不接受前端自报 `userId`
- 用户只能读取和修改自己的画像、计划和会话
- 公开资料仅允许管理员或导入脚本修改
- 健康检查不得泄露配置和密钥
- 注销时撤销数据库会话并清除 Cookie
- 过期会话必须拒绝访问，并定期清理
- Demo 用户与真实匿名用户使用不同 `accountType`

匿名会话方案 A 的主要限制：

- 用户清除 Cookie 后无法恢复原身份
- 不支持跨设备同步
- 如果只使用签名 Cookie 而不落库，将无法主动撤销；本方案因此使用数据库会话表
- 每次受保护请求会增加一次会话查询，需要评估跨区域延迟

### 15.2 CloudBase PostgREST 权限

- `CLOUDBASE_PG_API_KEY` 只存在于 Vercel 服务端环境变量
- 浏览器只能访问同源 `/api/*`，不能直接访问 CloudBase 网关
- Repository 自动注入会话中的 `user_id` 过滤条件
- 禁止客户端提交原始 `select`、`filter`、`order` 或 RPC 名称
- 表名、字段名和 RPC 名称必须来自代码白名单
- 对写操作使用列白名单，忽略任何未声明字段
- 公共资料表只允许应用读取；写入通过受控导入脚本完成
- 优先验证并启用 RLS 或最小权限角色，不能长期默认管理员 Key 就等于安全
- 一旦 API Key 泄露，应立即轮换并检查调用日志

### 15.3 输入与请求安全

- 所有输入通过 Zod 校验
- 对长文本设置长度上限
- 富文本输出进行安全渲染
- 不执行模型返回的 HTML、JavaScript 或命令
- Agent 工具参数必须再次校验
- 所有修改请求校验 `Origin` 是否为正式域名或允许的预览域名
- Cookie 采用 `SameSite=Lax`，但不能仅依赖 SameSite 防止 CSRF
- 敏感修改可增加一次性 CSRF Token
- 输出用户内容时默认进行 HTML 转义，禁止直接使用未经净化的 `dangerouslySetInnerHTML`

### 15.4 速率与费用保护

- 匿名用户限制每分钟调用次数
- 若启用 AI，为其设置单用户日限额
- 相同请求短时间内可缓存
- 超限时返回明确提示
- AI 始终可通过开关关闭，且关闭后资料检索、测评、画像、路线和进度功能仍完整可用
- 不能使用 Vercel 函数内存变量作为可靠限流器，因为不同实例不共享状态
- MVP 可使用 PostgreSQL 原子计数/RPC 实现会话级限流
- 对公共搜索结果使用 Vercel 缓存，减少跨区域数据库请求

### 15.5 个人数据

MVP 尽量少收集：

- 不要求真实姓名
- 不要求学号
- 不要求手机号
- 不收集身份证等敏感信息
- 联系导师邮件中的个人信息由用户自行填写和确认

应提供：

- 隐私说明
- 清除个人成长记录的入口
- 匿名模式说明

### 15.6 学术诚信

论文训练模块必须明确：

- 不代写正式提交论文
- 不伪造引用、实验和数据
- 不承诺论文发表
- AI 输出需要用户核验
- 生成示例不得冒充用户真实成果

## 19. 关键漏洞与实施难点

以下问题不会因为架构可行而自动消失，必须在 D1–D7 中逐项验证。

### 19.1 管理级 API Key 泄露

风险：当前探针使用的 CloudBase API Key 权限较高。一旦进入前端、日志、错误页面或公开仓库，攻击者可能直接读写数据库。

缓解：

- Key 只放 Vercel 服务端环境变量
- 在构建产物和浏览器 Network 中搜索确认不存在 Key
- Repository 不把上游错误原样返回前端
- 验证能否创建更小权限的 Key、角色、视图或 RPC
- 制定轮换流程，记录 Key 创建人和使用环境

上线阻断条件：无法保证 Key 不进入浏览器，或无法限制公开接口的写操作。

### 19.2 应用层越权与 IDOR

风险：PostgREST 管理 Key 可能绕过 RLS。如果接口接受前端传入的 `userId`，用户可修改请求读取他人画像和简历。

缓解：

- 所有用户 ID 都从服务端会话取得
- Repository 的用户私有查询强制附加 `user_id = session.userId`
- 为每个私有资源增加所有权测试
- 对 `planId`、`sessionId` 等资源先校验所有权，再读写
- 验证 RLS 与当前 API Key 的真实配合方式，不凭假设上线

上线阻断条件：使用用户 A 的 Cookie 可以读取或修改用户 B 的任何私有数据。

### 19.3 匿名会话劫持与 CSRF

风险：Cookie 被窃取后等同于用户身份；跨站请求可能触发数据修改；匿名用户无法通过真实身份找回账户。

缓解：

- 使用 256 bit 随机 Token，数据库只存哈希
- Cookie 设置 `HttpOnly`、`Secure`、`SameSite=Lax`
- 修改请求校验 `Origin`，必要时增加 CSRF Token
- 会话设置有效期、最后活跃时间和撤销能力
- 日志、URL、错误响应中禁止出现 Token
- 明确提示匿名数据与当前浏览器绑定

已接受限制：比赛 MVP 不支持跨设备同步和匿名数据找回。

### 19.4 Vercel 香港到 CloudBase 上海的跨平台延迟

风险：本地深圳到上海 57–194 ms 的数据不能代表 Vercel `hkg1` 到上海。一次页面若串行请求多次数据库，延迟会累积。

缓解：

- D1 必须从真实 Vercel Function 跑 CRUD 延迟探针
- API 按页面聚合数据，避免前端 N+1 请求
- 公共资料使用缓存和批量查询
- 复杂多步写入封装为数据库 RPC
- 日志记录每次 CloudBase 请求的独立耗时

建议阈值：普通页面 API P95 尽量小于 1.5 秒；超过阈值时优先减少往返次数。

### 19.5 PostgREST 查询注入和过度查询

风险：如果把前端传入的过滤字符串直接拼到 PostgREST URL，攻击者可能扩展字段、修改排序、读取不应暴露的数据，或构造高成本查询。

缓解：

- 字段、表、排序和 RPC 名称全部白名单
- 查询值用 `URLSearchParams` 编码
- 服务端限制 `limit` 上限和可选字段
- 不允许客户端传原始 PostgREST 表达式
- 对搜索关键词限制长度和字符范围

### 19.6 跨系统事务与部分失败

风险：Vercel 无法使用标准 `pg` 事务。一项操作涉及多张表时，可能第一步成功、第二步失败。

缓解：

- 单表操作直接使用 PostgREST
- 多表强一致操作封装为 PostgreSQL RPC 函数
- API 使用幂等键，防止用户重复提交
- 对导入任务记录批次号和状态
- 不在 Vercel 中用多个独立 HTTP 请求模拟事务

### 19.7 Serverless 限流和并发

风险：Vercel 实例之间不共享内存，简单 `Map` 计数无法形成可靠限流；重复点击可能产生重复画像和计划。

缓解：

- 使用 PostgreSQL RPC 原子计数实现关键接口限流
- 提交接口支持幂等键
- 按会话、IP 哈希和接口组合限流
- 前端按钮在请求期间禁用，但不能只依赖前端

### 19.8 数据库迁移和 Schema Cache

风险：运行时没有任意 SQL 入口；表结构变更依赖 CloudBase 管控面。PostgREST Schema Cache 更新不及时可能出现“表不存在”等错误。

缓解：

- 所有迁移 SQL 纳入仓库并编号
- 迁移先在测试环境执行并验证
- 发布流程明确“迁移先于代码”或兼容性顺序
- 新旧代码在迁移窗口内尽量向后兼容
- 不允许生产环境临时手工改表而不回写迁移文件

### 19.9 Vercel 可达性与地域配置

组委会确认 Vercel 可用，解决了赛事合规问题，但不等于所有网络环境都稳定。

仍需：

- 明确设置函数区域为 `hkg1`，避免默认美国区域
- 用校园网、家庭宽带和手机流量实测正式链接
- 保存一次可离线展示的 Demo 视频
- 提交前一天和提交当天再次检查

### 19.10 预览环境误连生产数据

风险：Vercel 每个分支都可能生成 Preview。如果 Preview 使用生产 Key，测试代码可能污染或删除生产数据。

缓解：

- Preview 使用独立 Key 和测试表/环境
- Production 环境变量只配置在 Production Scope
- 破坏性脚本要求显式环境确认
- 导入脚本打印目标环境并要求二次确认

### 19.11 数据来源和内容责任

风险：导师、实验室和比赛资料过期或错误，比纯技术错误更容易造成实际伤害。

缓解：

- 每条事实必须有来源和核验日期
- 不保存未经公开的联系方式
- 不生成导师主观评分
- 提供“信息可能更新，请以官方页面为准”的提示
- 失效来源降级为待复核，不继续用于强事实回答

### 19.12 实时 AI 口径变化

风险：后续赛事口径可能变化，团队临时开启模型导致合规、延迟或费用问题。

缓解：

- 提交版保持 `AI_PROVIDER=disabled`
- 可选 Provider 与业务代码隔离
- 启用前重新确认组委会口径并执行完整回归测试
- 不因 CodeBuddy CLI 已跑通就默认接入主链路

### 19.13 Vercel Function 运行限制

风险：Vercel Function 存在请求体、执行时间、包体积和临时文件系统限制。后续如果增加 PDF 上传、长任务或大型 SDK，可能突然触限。

缓解：

- P0 不支持论文 PDF 上传，只接收短文本或结构化表单
- Route Handler 使用 Node.js Runtime，不使用 Edge Runtime
- 不把大模型 CLI、大型解析器或无关二进制打入主函数
- 单次请求设置应用层超时并避免后台长任务
- 需要文件上传时改为客户端直传对象存储，不经 Vercel Function 中转

### 19.14 匿名会话与垃圾数据增长

风险：爬虫或频繁清除 Cookie 会不断创建匿名用户和会话，消耗数据库、网关额度并产生孤儿数据。

缓解：

- `/api/session/bootstrap` 设置 IP 哈希和时间窗口限流
- 已存在有效 Cookie 时绝不重复创建会话
- 定期删除过期会话及长期无活动、无业务数据的匿名用户
- Demo 模式优先复用固定演示数据，不为每次访问复制整套内容

### 19.15 外部链接、开放重定向与 SSRF

风险：导师主页和资料来源包含外链；如果未来服务端根据用户输入抓取 URL，可能形成 SSRF，访问内网或云元数据地址。

缓解：

- 当前版本只展示人工核验后入库的 `https` 来源
- 外链使用 `rel="noopener noreferrer"`
- 不提供接受任意 URL 的服务端抓取接口
- 若未来加入抓取，必须限制协议、域名和解析后的 IP，阻止私网、环回和元数据地址

### 19.16 并发覆盖与重复提交

风险：用户在多个标签页操作，可能覆盖学习进度；网络重试可能重复创建画像、计划或简历。

缓解：

- 写接口接受幂等键
- 记录 `updated_at` 或版本号，使用乐观并发控制
- 关键 RPC 在数据库事务中检查当前状态
- 前端收到版本冲突时刷新最新数据并提示用户

### 19.17 数据备份与恢复

风险：免费或共享环境的备份能力有限，误操作可能破坏公开资料和演示数据。

缓解：

- 所有公开内容的源文件保存在仓库 `content/`
- 数据库迁移和种子数据可重复执行
- 生产导入使用批次号并支持回滚或禁用批次
- 提交前导出关键公开数据和演示数据
- 任何清理脚本默认拒绝生产环境

## 23. 最终完成定义

只有同时满足以下条件，Web 主作品才算完成：

- 评委通过在线链接可以打开产品
- 无需团队协助即可开始体验
- 用户能够完成测评并获得科研画像
- 用户能够生成并保存学习路线
- 用户可以查询至少一类带来源的真实科研资源
- 任务编排器能够调用工具并使用用户档案，而不是只进行无上下文闲聊
- 匿名会话可以创建、恢复、过期和撤销
- 使用用户 A 的会话不能读取或修改用户 B 的数据
- CloudBase API Key 未出现在前端构建产物、浏览器请求或公开日志中
- Vercel 到 CloudBase 的生产延迟已测量且核心页面不存在明显 N+1 请求
- 页面明确区分公开事实、AI 建议和待核验信息
- 默认关闭实时模型；若后续获准启用，关闭或调用失败时仍能回到规则结果
- 用户数据不会被其他用户读取
- 仓库不存在真实密钥
- README 能说明本地运行、部署、数据来源和团队分工
- 生产环境经过电脑端和手机流量测试
- Demo 视频中的操作路径与线上版本一致
- LearnBuddy 使用记录覆盖需求、设计、编码、调试、测试和复盘

## 24. 实施 Agent 工作规则

后续将本文交给开发 Agent 时，应同时附带以下要求：

1. 先检查仓库现状，不假设项目尚未初始化。
2. 每次只实现一个可验收阶段，不同时铺开全部功能。
3. 修改前说明本阶段目标、文件范围和验收方式。
4. 所有数据库写入先通过 Zod 校验。
5. 提交版默认 `AI_PROVIDER=disabled`；任何获准启用的模型调用必须经过 `LLMProvider`。
6. 所有事实型公开资料必须带 `sourceIds`。
7. 不在获得明确许可前把实时模型或 Agent SDK 接入提交版主链路。
8. 不擅自加入多 Agent、向量数据库、自动爬虫和论文代写。
9. 每个阶段结束运行类型检查、测试和构建。
10. 发现文档与实际平台能力冲突时，先做最小技术验证并记录结果，再修改方案。
11. 不在浏览器代码中引入 CloudBase 管理 API Key，也不接受客户端传入的 `userId` 作为权限依据。
12. 数据访问必须经过 Repository；复杂事务必须通过数据库 RPC，而不是多个松散 HTTP 请求。
