# 大四选导师：需求与分工

> 版本 v0.5 ｜ 2026-11-08 ｜ 内部文档，团队对齐和开发依据用，不提交给辅导员、不对学生发布。内容不做严格限制，随开发随时改。

## 1. 这个项目是干什么的

把原来的「科研小助理」从"给大一新生做科研启蒙"，扩展出一个"**大四选导师**"入口，帮大四同学**又快又靠谱地**找到合适的导师。交付给学院辅导员老师，不是毕设答辩项目。原来大一那套（测评、画像、路线）保留不动，大四入口另开，两条路径并存。

它跟"直接问 AI"最大的区别，也是它最值钱的一点：**计软导师的全套信息都整理好了、每条都能查到出处**，不用去学校官网一个个翻。我们只说有来源的话，名额、课题不瞎编，每条推荐都能说清楚"为什么推荐他"。

## 2. 给谁用

- **主要用户**：深大计软学院大四学生，要选毕设导师。
- **次要**：辅导员/学院，想让学生方便地找到合适导师。

## 3. 现在的状态

**这个项目原来是干什么的**：粤港澳大湾区 AI Coding 创新大赛（方向二「AI + 学术科研助手」）的参赛作品，深大计软学院 3 人队做的，面向**大一新生**做科研启蒙和兴趣匹配。整套流程已经做完：免注册做一次科研测评（15 题）→ 拿到科研画像 → 按画像生成学习路线 → 兴趣匹配的教师资料 → 科研问答 → 任务打勾。资料有 10 位教师（带来源和核验日期）和 12 条 FAQ，部署在 Vercel。

**这次要做的**：把它扩展出一个"大四选导师"入口（见 §4）。原有功能基本保留，主要就差一件事——重构 AI 调用。

**目前跑不起来，要先修：**

> 比赛时 AI 是靠 LearnBuddy 的 CLI 调接口的（`@tencent-ai/agent-sdk` 会拉起一个 CLI 子进程，配 `SERVER_CODEBUDDY_API_KEY`）。现在这条路不通了。需要有人把 AI 调用**改成直接用自己的 AI API key**，去掉对 CLI 的依赖。这件事排在所有新功能前面，任务见 §10 的 R1。

**数据现状**：只有官网公开资料。以后可能向老师/学院申请授权，需要的东西先记在 §6 清单里。

## 4. 要做什么（功能）

分两块，同时推进，互不挡路。

### 第一块：导师信息与搜索（现在就能做）

核心部分，也最好落地，大部分是在现有资源页上扩展。

| 功能 | 用户能做什么 | 关键点 |
|---|---|---|
| 导师资料扩充 | 看到更全的计软导师名单 | 从 10 位扩到全院；每条带来源和核验日期，缺的写"未知"，不猜 |
| 多入口搜索 | 按**名字 / 课程 / 实验室 / 方向**搜到导师 | 名字支持模糊匹配；搜"程序设计基础"能出上过这门课的老师；搜"视觉"能列出所有做视觉的导师和实验室 |
| 方向聚合页 | 一张大页面，方向做成卡片，可以搜索、多选，点开看这个方向的全部导师 | 一个老师有多个方向的，要每个方向都能搜到 |
| 导师详情页 | 一眼看到邮箱、方向、主页链接 | 邮箱放最前；学校官网主页必做，个人主页/实验室页有就放；每条信息的出处能点开看 |
| 联系准备单 | 生成一份"要确认哪些问题 + 公开邮箱 + 联系草稿" | 只生成草稿，学生自己决定发不发，不自动发邮件 |
| 毕设时间轴 | 进去就看到选导师截止、开题、答辩这些时间点 | 内容要有出处，来自学院正式通知 |

### 第二块：兴趣匹配与推荐（先研究，再写代码）

这一块的价值是"帮你找方向"，但**怎么让学生舒服地、低负担地讲清自己的情况**需要研究（涉及心理学和问卷设计），所以先出研究笔记和设计卡，不急着写代码。

| 功能 | 用户能做什么 | 关键点 |
|---|---|---|
| 轻量自评问卷 | 用 2~3 分钟说清"想做什么方向、能投入多少、基础如何" | 别做成原来那套 15 分钟测评，大四没人有耐心做 |
| 匹配推荐 | 看到"值得联系的导师 + 为什么 + 还要确认什么" | 每句推荐都连得上"学生的情况"和"导师的资料"；资料不够就写"需进一步了解"，不硬说"匹配" |
| 分层报告 | 区分"方向建议 / 联系候选 / 已确认课题"三层 | 资料只够到哪层就输出到哪层；没有本届课题就不显示"已匹配到可选毕设" |

## 5. 不做的事（红线）

沿用原来的：不编引用、不猜名额、不代写论文、不评价导师人品/排名。

这次明确砍掉：**导师"严厉/松弛"评价、匿名留言墙/评论**。理由：违反上面红线；要真实上线给学生用，这类内容有诽谤和审核风险。

## 6. 数据（需要什么资料）

现在只有官网公开资料。下面这些记下来，作为以后向老师/学院申请的清单：

| 需要 | 为什么 | 来源要求 |
|---|---|---|
| 本届接收名额/状态（谁收、收几个） | 决定"可联系候选"和匹配 | 要授权或明确确认，不抓私有平台 |
| 本届已确认课题（题目/要求/交付） | 进入"已确认课题"这一层 | 老师本人或学院授权，分别留证据 |
| 导师↔课程、导师↔实验室 | 多入口搜索 | 官网可核验为主，有变动的标年份 |
| 个人主页/实验室页/公开社媒 | 详情页多链接 | 公开链接，标核验日期 |
| 毕设时间节点（截止/开题/答辩） | 时间轴提醒 | 学院正式通知 |

原则：课程、实验室、主页这些能核实的事实可以批量收；名额、课题一律走授权，**拿不到就写"未知/待确认"，不猜**。

另外：现在导师资料存在静态 JSON（`data/szu-teachers.json`），不在 Cloud 数据库（库里只有 sessions/task_progress 两张表）。A1 扩充前先定：继续用 JSON，还是搬进数据库。

## 7. 分阶段（里程碑式，快速迭代）

每个里程碑结束，都有一版**学生/辅导员能真正打开用的东西**，哪怕很小。做完一个就上线一个，滚着往前走。

| 里程碑 | 做到什么样（能打开用） |
|---|---|
| 1 能跑起来 | R1 完成，线上能打开 |
| 2 导师能查 | 资料 + 搜索 + 详情能用 |
| 3 能出联系准备单 | 加时间轴，能生成准备单 |
| 4 能出推荐 | 轻量问卷 + 报告（若做匹配） |
| 5 试用 | 找学生/辅导员试用，出问题清单 |

没有单独的"探路阶段"——探路/试错是每个人做自己里程碑任务时的日常做法：多试、多试错，不用拘泥文档，试出来的结论写进 PR 或交接笔记就行。

匹配是可选项：B1 研究出结论后再定做不做，不做就砍掉里程碑 4，直接进试用。

## 8. 怎么分工

大家都用 AI 开发，没有谁技术好谁差；关键是**谁愿意在哪个方向上花时间、谁和 AI 配合顺畅**。所以：

- **按任务认领，不按人分模块**：每个里程碑列一堆任务，谁想做就领，做完一个领下一个。阶段进度和具体分工不用划得很死。
- 我（PM）负责定方向、理任务、排优先级，不替别人写代码。

几条轻规则，避免认领了又烂尾：

1. 每个任务写一句"怎么算做完"。
2. 认领了但没空，就把状态改成"可转手"，写一句"做到哪、下一步、有什么坑"，别悄悄消失。
3. 数据结构/契约**不单独列任务**：谁先做相关功能谁顺带把它定了（先做 A1 的定导师资料结构，先做 B3 的定课题结构）。两个人要碰同一份时，动手前先在群里对齐一次。
4. 每个任务的验收**默认都含两条**：不同学生互看不见；AI 挂了页面还能用。

## 9. 怎么协作、看进度

沿用比赛时的做法，重构和后续开发都这么干：

- **每个人做完就提交（PR），PR 里写清"改了什么、为什么"**。文档也随 PR 一起改，不单独走文档评审。
- **开工前先看别人的 PR**：自己（或自己的 agent）动手前，先扫一眼别人最近的 PR，掌握进度，避免重复或撞车。
- **部署在 Vercel**：PR 合入后线上直接能看到效果，方便团队同步进度、直接体验、决定下一步迭代，也方便给辅导员验收。现在 Vercel 主要就是团队内部 + 验收用；将来如果要公开发给学生，再部署到学校服务器（现在还没定，先不管）。
