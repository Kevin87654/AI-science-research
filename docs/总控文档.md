> 版本 **v2.4** ｜ 2026-09-22 ｜ 粤港澳大湾区 AI Coding 创新大赛 · 方向二（AI + 学术科研助手）
>
> **这是什么**：团队三人协作的**入口与索引** —— 它告诉你「该去看哪份文档、怎么和 AI agent 配合、改动怎么提交」。

## 一、文档分两类

以下都在 `docs/` 目录下。**判断依据只有一个：这份东西会不会变？**

### 1. 实测事实 —— 不随讨论变动，出现冲突以它们为准

| 文档 | 管什么 |
|---|---|
| 《云开发实测记录》 | CloudBase 环境的实测事实与限制 |
| 《数据库接入探针记录》 | 数据访问的硬约束 —— 接入姿势、限制、能力边界、权限真相、错误形态、迁移流程 |
| 《数据库交接说明》 | 数据库怎么接 —— 接入方式、建表流程、权限、踩坑 |

> 这类是**客观事实**，改也改不掉。要改先拿出新的实测结果。

### 2. 随开发演进 —— 直接改，不必等评审

| 文档 | 管什么 |
|---|---|
| 《科研小助理产品需求文档 PRD》 | 产品要做什么 —— 定位、目标用户、功能优先级、验收清单 |
| 《技术经验与开发规范建议》 | 工程方法论 —— 探针制度、错误可见性、提交前检查清单 |

> **产品范围本来就是变化最快的东西。** 想改功能就在 PRD 里直接改，改完在 PR 描述里说明一句即可，不必为了调整一个页面先走一轮评审。
>
> 真正需要冻结的只有第 1 类，以及产品红线（不编造引用、不猜导师名额、不代写论文、不使用第三方 AI）——红线写在 PRD 的对应章节里，要动它先全队确认。

## 四、每个人怎么用自己的 agent

### 开工前，把这几样喂给你的 agent

1. **本文档** —— 统一入口
2. **相关文档** —— 产品看 PRD；碰数据库看《数据库接入探针记录》、《数据库交接说明》与《云开发实测记录》；写工程代码看《技术经验与开发规范建议》
3. **对应的执行细则** —— 在 `docs/` 目录里找

### 协作时的几点建议

- 先让它**检查仓库现状**，不要假设项目还是空的
- 让它**一次只做一件事** —— 说清目标、要改哪些文件、怎么验收，做完就停
- 每做完一段**跑一遍检查**（Lint / Type Check / 相关测试 / Build），让它报结果
- 涉及**真实账号、密钥、控制台操作、数据库执行**的环节自己动手，不要把密钥发给 agent
- 平台行为与文档不一致时，先让它写个**最小探针**验证，再改方案
- 用哪个 agent 由你自己定，但**产出要落到仓库里**（代码、文档、迁移 SQL）

### 提交方式

完整规则见 `CONTRIBUTING.md`，简版：

- **代码**、配置、依赖、SQL 迁移 → `dev/<你的名字>` 分支 → PR → 合并
- **文档小改**（只动 `*.md`）→ `main` 是受保护分支（要求至少 1 个 Approve），**只有 Kevin 能直接提交**，其他成员走 PR —— 完整规则见 `CONTRIBUTING.md` §3 与 §5.8
- **PR 描述里写清两件事**：这次**改了什么**、**为什么改**（替代"改需求先改 PRD"的做法）
- 动手前**先拉取**

## 五、维护约定

1. 本文档只起**索引与协作指引**作用，不记录产品细节、技术选型、开发步骤和赛事规则。
2. §一 第 1 类的实测事实不随讨论变动，确需修改先拿出新的实测结果；第 2 类随开发演进，直接改即可。
3. 新结论写进**对应主题的文档**，不要都堆到这里。
4. 修改本文档请更新顶部版本号。
