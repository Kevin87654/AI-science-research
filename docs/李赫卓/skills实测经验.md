## 1. 一句话结论 `【已核实】`

平台内的**专家 / Skill 都是本机资产**，**没有服务端托管层** → 它们**给不出"打开就能用"的 URL**。
要让别人用，对方**必须先装客户端**。这一条决定了后面所有技术路线。

---

## 2. 四层结构：客户端 / 市场 / 专家 / Skill `【已核实】`

| 层 | 是什么 | 职责 |
|---|---|---|
| **客户端** | 提供运行环境与 **agent 循环** | **一切的宿主** |
| **市场 marketplace** | 带 `.codebuddy-plugin/marketplace.json` 的目录 / zip / git 仓库 | **分发** |
| **专家 Expert** | 市场里的一个条目，有身份、头像、可被用户主动选中 | **＝"谁在做"（角色包）** |
| **Skill** | 能力包，被 agent **按需加载**，没有身份 | **＝"怎么做"（能力包）** |

**踩点**：专家是**入口**（用户能找到你），Skill 是**装备**（干活更专业）。
**先有专家，再考虑加 Skill。**

> 常见误解：以为"专家和 Skill 是同一层的东西"，或以为"专家本身就是一个应用"。都不是。

---

## 3. 专家 vs Skill：不是一回事 `【已核实】`

| 维度 | Skill | 专家 Expert |
|---|---|---|
| 本质 | 能力 / 知识包 | 角色 / 人格 |
| 核心文件 | `SKILL.md` | `.codebuddy-plugin/plugin.json` + `agents/*.md` |
| 存放位置 | 用户级 `~/.learnbuddy/skills/` 或项目级 | `$WORKBUDDY_CONFIG_DIR/plugins/marketplaces/<market>/plugins/<name>/` |
| 出现在专家中心 | ❌ | ✅ |
| 有头像 / 开场白 / 推荐问法 | ❌ | ✅ |
| 触发方式 | AI 按需加载，可叠加多个 | 用户主动选择，构成会话主人格 |

**唯一交集**：专家的 `plugin.json` 有 `skills` 字段，可预加载技能。

> 类比：**专家是员工**（有姓名工位），**Skill 是操作手册**（谁需要谁翻）；员工可以在背包里塞几本手册。

**判定"是不是 Agent 型专家"** `【已核实】`：
`expertType: "agent"` + `agents` 数组只有 1 个 MD 文件 + **没有** `teamInfo` / `members` / `settings.json`
（后三样是 Team 型专属）。

## 4. Skill 能不能"打开链接就能用"？不能 `【已核实】`

**Skill 没有可访问的运行地址。** 但链接与 Skill 有四条**真实**关联，容易混淆：

| 链接的用法 | 能否 | 说明 |
|---|---|---|
| 介绍页链接 | ✅ | 注册表里的 `homepage`，是**说明页**，不是运行入口 |
| 装 Skill 的来源 | ✅ | 注册表 zip 下载 / npm 风格仓库 / 客户端市场 |
| Skill **内部访问**网页 | ✅ | 脚本 `curl` API 或让 agent 抓页面 —— 方向是 Skill **用**网页 |
| Skill **产出**网页链接 | ✅ | 那是**产物**的链接，与 Skill 本体无关 |
| **Skill 本体变成 URL** | ❌ | **没有服务端托管这一层** |

**根因**：Skill 跑起来依赖**三样本机东西**——① 文件系统、② 运行环境（Python / Node）、③ **agent 循环**。
这三样都不在浏览器里。

**推论** `【推断】`：想让别人用你的专家 / Skill，正确做法是**打包发 zip** 或**建市场仓库**；
**发链接没用**。

## 5. 网页要调用本机 Skill：必须自建一层"桥" `【已核实】`

**答案是"半个是"**：需要一个**运行在本机、只监听回环地址的进程**。
走 HTTP 的话它技术上就是服务器——但只是**本地回环服务器**，不是对外服务器。

### 为什么绕不开这层桥：浏览器沙箱的三条硬边界

1. **读不了本地文件**（`skills/*/SKILL.md` 对网页不可见）
2. **起不了本地进程**（不能 `spawn` 去跑 Skill 里的脚本）
3. **跑不了 agent 循环**（LLM 读说明 → 选工具 → 看结果 → 再决策，这套只在宿主里存在）

### 四种桥的形态

| 形态 | 做法 | 适用 |
|---|---|---|
| **本地 HTTP 服务** | 监听 `127.0.0.1:<port>`，网页 `fetch` | 最通用，要处理 CORS |
| **网页也由本机服务提供** | 同一服务既发静态页又发 API | 最省事，同源无跨域 |
| **客户端 IPC 注入桥** | Electron preload 暴露 `window.api` | 桌面客户端内嵌网页的正解 |
| **扩展 / 自定义协议** | native messaging、`myapp://` | 网页在公网又想触达本机时的折中 |

### 安全红线（写死，不得违反）

- 只绑 **`127.0.0.1`**，**永远不要 `0.0.0.0`**（否则同局域网任何人都能调你本机能力）
- 校验 **`Origin`** 头，只放行自己的域名
- 启动时生成**随机 token**，防其他本地页面偷调
- **不要用内网穿透**把本地端口直接暴露公网

> **取舍** `【推断】`：如果只是自己用，**做网页不划算**（专家已装好，直接用就行）。
> 真正值得做网页版的唯一情形：**你要给别人用，而别人不愿意装客户端**。

## 6. 怎么给别人用：三条路线 `【已核实】`

**最硬的约束：对方必须装了客户端。** 这一条决定所有路线。

| 路线 | 做法 | 适用 | 成本 |
|---|---|---|---|
| **A 发 zip** | 打包 → 对方解压放目录 → 改 `marketplace.json` → 重启 | 少数已装客户端的人 | **最低** |
| **B git 市场仓库** | 推到仓库 → 对方添加市场源 → 你 `git push` 即更新 | 一批人 + 需持续更新 | 约一个下午 |
| **C 网页版云服务** | 方法论搬到服务端，上传输入 → 返回结果 | 对方**不**装客户端 | 等于重做，且要付 API 费 + 担隐私责任 |

**选择依据** `【推断】`：这个决策**不该由技术难度决定**，而由**目标用户是否愿意装客户端**决定。
- 愿意装 → A / B，成本极低
- 不愿意装 → 只能 C，成本高且要承担 API 费用与隐私责任

**建议做法**：先用 A 做小范围验证（发给一两个人试装，记录卡在哪一步），拿到真实反馈再决定是否投入 B / C。

## 7. 环境事实与关键命令

| 项 | 值 |
|---|---|
| 配置目录 | **由 `WORKBUDDY_CONFIG_DIR` 决定**（官方文档写 `~/.workbuddy`，**以实际为准**）`【已核实】` |
| 专家包目录 | `<配置目录>/plugins/marketplaces/<market>/plugins/<name>/` |
| 用户级 Skill 目录 | `<配置目录>/skills/` |
| 市场源配置 | `<配置目录>/plugins/known_marketplaces.json`（支持 `type: directory \| zip`） |

**专家包结构**（把 `<name>` 换成你的专家名）：

```
<name>/
├── .codebuddy-plugin/plugin.json   # 身份、展示名、头像路径、标签、推荐问法
├── agents/<name>.md                # 角色 prompt（人格与方法论）
├── avatars/expert.png              # 头像
├── README.md
└── .created-by-session
```

**关键命令**：

```bash
# 校验
python3 scripts/validate_expert.py <expert-dir>

# 注册（必须执行，否则专家中心不可见）
python3 scripts/register_expert.py <expert-dir> --session-id <id>

# 打包
python3 scripts/package_expert.py <expert-dir> [output-dir]
```

## 8. 踩坑清单 `【已核实】`

| # | 卡点 | 现象 | 绕法 |
|---|---|---|---|
| 1 | **技能文档与实际脚本不一致** | `expert-manager` 的 `SKILL.md` 写 `.workbuddy-plugin/`，而 `init_expert.py` 实际生成、`validate_expert.py` 校验的是 `.codebuddy-plugin/` | **以脚本行为为准**，别照文档建错目录 |
| 2 | 配置目录不确定 | 官方文档写 `~/.workbuddy`，实际由 `WORKBUDDY_CONFIG_DIR` 决定 | 读环境变量，别硬编码 |
| 3 | Git Bash 路径转换 | 把 `/tmp/x.py` 传给 Windows 的 `python.exe`，被解析成 `c:\tmp\x.py` | 先 `cp` 到工作区，或用 `cygpath -w` |
| 4 | 图像生成工具不可用 | 查不到 `ImageGen` 工具 | 用纯 Python（`zlib` + `struct`）生成占位 PNG，同时在 README 附推荐 prompt 供后续替换 |
| 5 | 注册这一步容易漏 | 不跑 `register_expert.py` → 专家中心**看不到** | 打包前必须跑一次注册 |
| 6 | 市场源自定义入口 | `known_marketplaces.json` 支持 `directory` / `zip`，但**客户端里"添加市场"的 UI 入口未验证** | **待确认**，别凭空给截图 |
