## 0. 一句话背景

第一轮已交付并上线：`免注册进入 → 测评 → 画像 → 路线 → 兴趣匹配资料 → 问答 → 任务打勾 → 刷新保留`（任务进度）。
第二轮要解决三个「第一轮明确搁置 / 未覆盖」的问题：

| # | 问题（第一轮遗留） | 负责人 |
|---|---|---|
| 1 | 画像与路线还躺在浏览器 `localStorage`，换设备/清缓存即丢 | **黄瑜**：账号与数据存储落库 + PPT |
| 2 | 内容只有「计算机学院 10 位教师 + 12 条 FAQ」，没有「兴趣领域刊物」这一层 | **傅加贝**：兴趣方向刊物科普（按测试结果）+ 海报生成 |
| 3 | 测评的兴趣只是 7 个固定勾选方向、不够准；路线不按兴趣领域推荐「入门论文链接」 | **李赫卓**：测评内先探测兴趣领域 + 路线入门论文推荐 |

**三条红线不变**（所有改动都必须遵守，写进 PRD，要动先全队确认）：

1. **只说有来源的话**：不编造引用、不猜名额、不评人品、不代写。
2. **模型不参与事实判定**：AI 失败必须降级且对用户可见（角标如实显示「规则回答」）。
3. **契约层只放可序列化数据**：改契约必同步改 `src/contracts/samples.ts`（不改进不了 tsc）。

## 1. 黄瑜（@Kevin87654）—— 账号与数据存储 + PPT

### 1.1 目标

把「测评提交 + 画像 + 路线」从浏览器 `localStorage` 提升为**服务端数据库持久化**，
让同一匿名会话**换设备 / 清缓存后仍能读回**；并制作比赛演示 PPT。

> 「账号存储」本轮的最小落地形态是**匿名会话下的画像/路线落库**，不是必须引入注册登录。
> 是否升级为「注册登录 + 跨设备同步」涉及 PRD §3.3「不做注册登录」这条能力边界，
> **需要全队拍板**；没拍板前先按最小形态做，不阻塞自己。

### 1.2 现状（代码依据）

- 数据库只有两张表：`sessions`、`task_progress`（`scripts/migrations/001_init.sql`）。
- 仓储只有 `SessionRepository`、`ProgressRepository`（`src/server/repositories/types.ts`）。
- 画像/路线走 `src/features/shared/local-bridge.ts`——文件头**明确标注「过渡方案，等 A 提供接口后替换」**。
- 契约 `Profile` / `Roadmap` 都带 `userId` 字段，但**没有对应表和接口**。
- 任务进度已有完整范式可抄：`progress.ts`（service）→ `progress-client.ts`（前端）→ `progressRepository`（仓储）。

### 1.3 可实施步骤

1. **新增迁移** `scripts/migrations/002_profile_roadmap.sql`：建 `profiles`、`roadmaps` 两张表，
   风格对齐 001（`user_id` 外键含归属、`enable/force RLS` 但不建 policy、应用层过滤）。
   建议每张表用 `jsonb` 存整个对象 + 少量索引字段（`user_id` / `id` / `is_demo`），避免逐字段映射。
2. **新增仓储接口与实现**：`ProfileRepository` / `RoadmapRepository`
   （`types.ts` 加接口 + `in-memory.ts` + `postgrest.ts` 各实现），`userId` 作为必需第一参数。
3. **新增服务**：`src/server/services/profile.ts` / `roadmap.ts`，`userId` 一律来自 `identity.ts` 的 `readSession`。
4. **新增接口**：`GET/PUT /api/profile`、`GET/PUT /api/roadmap`，响应统一 `ApiResponse<T>`。
5. **前端替换**：把 `local-bridge.ts` 换成「服务端真相 + 本地缓存」的桥接（照 `progress-client.ts` 的范式），
   画像/路线改走接口；过渡期可保留「本地读不到就读服务端」的双读兜底。
6. **PPT**：按 §5 的演示路径组织，覆盖「产品定位 → 测评 → 画像 → 路线 → 资料/刊物 → 问答 → 成长首页 → 技术架构与验证」。

### 1.4 验收标准

- 换设备 / 清 `localStorage` 后，画像与路线仍能读回（同一 Cookie）。
- 跨用户隔离：读/写带他人 `userId` 一律被拒（403 或不可见）。
- 内存实现与真库实现**两套都过测试**（对齐现有 `in-memory.test.ts` 的做法）。
- `pnpm lint / typecheck / test / build` 全绿；PPT 可放映、能支撑 3～5 分钟演示。

### 1.5 注意事项

- 表结构用 `jsonb` 还是逐字段，**先在 PR 里对齐**，再动迁移。
- 这是「免注册」前提下的持久化，**不引入注册登录**（除非 §1.1 的拍板点被确认要做）。
- 真实迁移由黄瑜走既有评审 + 人工投递流程，其他人只提字段需求、不各自建表（对齐《数据库交接说明》）。

## 2. 傅加贝（@fodenspider）—— 兴趣方向刊物科普 + 海报生成

### 2.1 目标

在问答结果上增加「**兴趣方向领域内的刊物科普**」：用户拿到回答后，能看到该兴趣领域的**入门刊物（期刊/会议）**介绍；
并为其**生成一张可分享的科普海报**。
**刊物所属领域的依据，是李赫卓的「新版兴趣测试结果」**（见 §3）——即由测评开头的**启发式提问**测出的兴趣领域，不再是那 7 个勾选方向。

### 2.2 现状（代码依据）

- 数据资产只有 `data/szu-teachers.json`（10 教师）+ `data/research-faq.json`（12 FAQ + 9 来源）。
- 契约**没有「刊物」实体**；来源里已有 `ccf-directory`（会议期刊分级）但**没被任何任务/页面引用**
  （见 `src/features/roadmap/plan-roadmap.ts` 文件头的「已知缺口」注释）。
- 问答返回的 `Answer` 只有 `actions` / `citations` / `teacherIds`，没有刊物推荐。

### 2.3 可实施步骤

1. **新增刊物数据** `data/journals.json`：每条含 名称、全称、方向标签（**复用李赫卓「新版兴趣测试结果」的领域词表**）、
   等级（如 CCF A/B/C）、一句话简介、新人怎么读、公开来源（`Source` 结构，可核验）。
2. **新增契约** `Journal` / `JournalIntro`：对齐 `catalog.ts` / `knowledge.ts` 的写法；同步改 `samples.ts`。
3. **领域 → 刊物映射**：每个兴趣领域至少 2 本入门刊物，先覆盖李的测试结果能产出的领域标签
   （初始领域词表可沿用旧测评的 7 个方向：人工智能 / 机器人 / 数据科学 / 生物医学 / 材料与能源 / 人机交互 / 网络安全）。
4. **问答结果扩展**：`Answer` 增加刊物推荐（新字段或 `citations` 旁的并列结构），
   按「测试结果探测出的兴趣领域」推荐刊物，来源必须能在来源注册表还原（复用 `sourceRegistry` 的思路）。
5. **科普展示**：`/resources` 或问答卡片下新增「这个方向的入门刊物」区块（标题 + 简介 + 来源 + 核验日期）。
6. **海报生成**：为某方向 / 某刊物生成一张科普海报（可下载/分享的图片），
   内容必须来自已核验刊物数据，海报上带来源；技术可用 AI 生图（本机 `ImageGen` 不可用，可用 Pollinations 接口）
   或程序化 SVG/HTML 出图——**实现方式自定，先出一张可验收的样例**。

### 2.4 验收标准

- 每个兴趣领域都有 ≥2 本入门刊物，来源可核验（`url` / `publisher` / `checkedAt` 齐全）。
- 问答结果能按「测试结果探测出的兴趣领域」推荐刊物；查不到就不硬凑（宁缺毋滥，不留空数组装样子）。
- 海报上的文字内容**全部可追溯到已核验来源**，不编造。
- `pnpm lint / typecheck / test / build` 全绿。

### 2.5 注意事项

- 刊物科普是「产品编辑内容」，用 `editorial: true` 标记（对齐 `Faq.editorial`）。
- 红线：**不编造影响因子、录用率等动态数字**；不确定就写「以官方/最新目录为准」。
- 刊物方向标签要**对齐李赫卓「新版兴趣测试结果」的领域词表**（见 §4），避免两套词表漂移。

## 3. 李赫卓（@waixr016）—— 启发式提问探测兴趣领域 + 路线入门论文推荐

### 3.1 目标

① **修改测评题目**，在**测评流程开头**先放一组启发式问题「测试」出用户感兴趣的领域——不是让用户直接勾选方向，
而是靠对话式提问从回答里**推断**出兴趣领域，得到一份「**新版兴趣测试结果**」；
② 探测完兴趣后，**再进入旧的能力维度测评流程**；
③ 新增论文推荐模块，根据这份测试结果，在**成长路线**里推荐该领域内的**入门级论文链接**，便于用户学习。

> 这份「测试结果」是李与傅之间的**共同输入**：李用它推荐入门论文，傅用它做刊物科普（见 §2）。

### 3.2 现状（代码依据）

- 现有兴趣来自测评里的 `q-interest` 题（`src/features/assessment/question-bank.ts`，7 个固定方向勾选），是「用户直接勾选」，不是从启发式问答里推断出来的。**已拍板：这道题将被移除，由启发式提问探测替代（见 §3.5）。**
- 测评目前**没有**「先探测兴趣再出题」的结构：`question-bank.ts` 只有固定题库 + 自适应出题，没有启发式兴趣探测这一层。
- 路线：`plan-roadmap.ts` 的 `RESOURCE_IDS` 是**固定映射**，`method-basics` / `goal` 为空；任务的 `resourceIds` 是「来源 id」，没有「按兴趣领域推荐入门论文链接」。

### 3.3 可实施步骤

1. **设计启发式问题集**：加一组启发式问题（二选一 / 多选 / 短答均可），每道题的选项**映射到兴趣领域标签**；
   问题要能「测出」用户自己都未必意识到的兴趣方向。
2. **兴趣探测引擎**：新增纯函数（建议 `src/features/assessment/interest-probe.ts`），
   输入启发式问题的作答，输出「**新版兴趣测试结果**」（`InterestProbeResult`：探测出的领域标签 + 依据）。
3. **接入测评流程开头**：`/assessment` 页**先跑兴趣探测（启发式提问）**，产出测试结果后**再进入旧的能力维度测评**；
   测评提交把探测结果一并带上（提交结构加探测结果或领域标签）。
4. **测试结果持久化**：结果随画像/路线一起存（依赖黄瑜的落库，过渡期走 `local-bridge.ts`）。
5. **入门论文数据**：新增 `data/intro-papers.json`，按兴趣领域组织入门论文
   （标题 + **可直接点击的链接** + 为什么适合入门 + 公开来源）。
6. **路线挂论文**：`plan-roadmap.ts` 生成时，根据测试结果把该领域的入门论文**链接**挂到任务
   （论文推荐模块）；顺手补齐 `RESOURCE_IDS` 里 `method-basics` / `goal` 的已知缺口。
7. **界面展示**：成长路线任务卡展开「推荐入门论文」（标题 + 链接），用户可直接点开学习。

### 3.4 验收标准

- 测评流程顺序正确：**先启发式提问探测兴趣，再进入能力维度测评**。
- 用户经启发式提问后，能拿到一个**明确、可解释**的兴趣领域结果。
- 成长路线里能看到该领域入门论文的**链接**，且可直接点击访问。
- 不同测试结果的用户，论文推荐有**可感知的差异**。
- 论文链接来源可核验（`url` / `publisher` / `checkedAt` 齐全）；`pnpm lint / typecheck / test / build` 全绿。

### 3.5 注意事项

- 「新版兴趣测试结果」是**李 → 傅 的接口**：傅的刊物科普依赖它，先定义好 `InterestProbeResult` 契约再并行。
- ⭐ **已拍板（2026-10-09）：新版测试结果「替代」测评里的 `q-interest` 题**——兴趣领域只来自启发式提问探测，不再让用户在测评里勾选方向。
- **「替代」的连带落地（李要一起处理，不能只做探测）**：
  1. **移除 `q-interest` 题**（`question-bank.ts` 里那 7 个勾选方向）。
  2. **`scoring.interests` 失去来源**——下游三处引用要改：`build-profile.ts`（画像的 `interests` / 优势 / 总结）、
     `plan-roadmap.ts` 的 `buildRoadmapTitle`（用 `scoring.interests[0]` 取路线标题）、`catalog.ts` 的 `SearchOptions.interests`（B→C 联动）。
     处理方式建议：兴趣字段改为由 `InterestProbeResult` 回填，而不是测评作答产生。
  3. **探测时序（已拍板）**：兴趣探测**前移到测评流程开头**——先启发式提问探测兴趣，再走旧的能力维度测评；
     这样画像/路线生成时兴趣已可用，不存在「探测晚于画像」的回填问题。
- 改测评提交结构（`AssessmentSubmission` 加探测结果）是**变更契约**，PR 里说明对画像/路线生成、傅刊物推荐的影响。

## 5. 提交与验收

- **代码**走 `dev/<名字>` → PR → 至少 1 人 Approve → Squash 合并 `main`（见 `CONTRIBUTING.md`）。
- **文档小改**可直接提 `main`（当前仅 Kevin 可直推，其余成员走 PR）。
- 每个 PR 描述写清**改了什么、为什么改**；契约变更额外说明对下游的影响。
- 合并前过 `pnpm lint / typecheck / test / build`。

**验收共用的演示路径**（PPT / 录屏 / 走查都用它）：

```
免注册进入 → 测评（先启发式提问探测兴趣 → 再按低档作答能力维度）
→ 画像「科研观察期」→ 生成路线（3 阶段，含该领域入门论文链接）
→ 刊物科普（按测试结果）→ 任务打勾 → 刷新仍在（服务端读回）
```

> 测评按低档作答时画像为「科研观察期」、路线 3 阶段；全选最高档则维度多 `ready`、路线只剩 2 项（画面很空），
