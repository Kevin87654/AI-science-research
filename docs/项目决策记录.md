## 1. 作品形态：一个内容源，两条封装线

### 1.1 决策 `【已定】`

开发**同一套核心能力**，封装成两种交付载体：

| | 轨道 A：Web 应用 | 轨道 B：平台内 Skill / 专家包 |
|---|---|---|
| 载体 | Next.js 应用，部署到 Vercel | Skill 包 或 专家包（`.zip`） |
| 交付物 | **可直接访问的在线链接**（必交项） | 打包文件 + 安装说明 + 演示材料 |
| 运行时 AI | 服务端在 Vercel 函数内跑 CodeBuddy Agent SDK | 平台自身（客户端内的 agent 循环） |
| 面向 | 评委在线体验、作品 Demo 视频 | 平台内复用、提交表单的「Skills 包」字段 `【待确认】` |
| 定位 | **主体** | **补充与风险对冲**，不可替代 A |

**一句话定位口径（对外统一说法）**：一个作品、两种载体。**不得**表述为"两个作品"。
理由：赛事规定 9 个题目任选其一、每人仅可参加一个赛题一个团队，措辞不当会被质疑重复参赛或精力分散。

> 决策来源：团队讨论（2026-09-18）。

### 1.2 为什么这么做 `【已定】`

1. **A 是硬性必交**。手册要求"作品须部署至浏览器环境，提供可直接访问的在线链接"，
   提交清单里「作品链接」标注为必需。没有 A 直接出局。
2. **B 对冲三个风险**：
   - 「最终效果呈现时最好不要包含第三方 AI」→ B 全程在平台内，天然合规；
   - 平台的专家 / Skill **没有服务端托管层、给不出 URL**（见 §5.2），若 A 的运行时 AI 来源被否，B 仍在；
   - 提交表单存在「Skills 包」字段，而手册未列出该字段的要求 → 交了大概率是加分项 `【推断】`。
3. **增量成本低** `【估算】`。如果方法论 / 提示词先统一定义在仓库根 `content/`（见 §1.3），
   B 的实质工作是"换封装 + 打包"，约 **+10~15%** 工作量，不是翻倍。
4. **不叫"齐头并进"的原因**：B **依赖** A 的内容层。选题未收窄、方法论未定型之前启动 B，
   必然返工。正确的并行对象是"内容"，不是"开发"。

### 1.3 ⚠️ 轨道 B 的评审现实（不要高估它的可用性） `【已推断】`

按 §5 的结论，**别人要用你的专家 / Skill 包，必须先装了客户端，再手动放目录、改配置、重启**。
因此：

- **评委大概率不会真的安装**。轨道 B 的评分贡献主要来自**材料本身**——方法论的完整度、可复用性、
  与作品的对应关系，而不是"评委真的用上了"。
- 因此 B 的提交物**必须自带**：
  1. **安装说明**（分步骤，含"对方需要什么前置条件"）
  2. **截图或录屏**证明它确实能在客户端里跑起来、确实能产出结果
  3. **README 说明它是同一个作品的另一种载体**，避免被当成独立小工具
- **不要**把 B 做成一个与 A 无关的东西。两条线的功能要能对上，评审才能看懂"一个作品、两种载体"。

### 1.4 共享约束：`content/` 是单一事实来源 `【已定】`

- 提示词、schema、领域知识、方法论模板**统一放仓库根 `content/`**，不硬编码在 `.ts` 里，也不写死在专家 prompt 里。
- 轨道 A 读 `content/`（运行时通过 `outputFileTracingIncludes` 打包进函数）；
  轨道 B 的专家 / Skill prompt 由 `content/` **生成或引用**。
- 目的：方法论改一次，两条线同步生效；也是"技术演进可追溯"这类评分点的证据。
- **开源要求**：手册规定赛道二作品须开源（MIT / Apache 2.0 / GPL 等）。
  轨道 B 的包**放进同一仓库**，即可一并满足开源要求。

### 1.5 建议排期 `【估算】`

```
① 选题收窄（方向二 7 个候选 → 1 个）        ← 阻塞项，最先做
② content/ 方法论与提示词定型                ← 两轨共同的前置
③ 轨道 A：骨架 → 最小链路（上传→解析→入库→图谱）→ 部署
④ 轨道 B：封装专家/Skill + 打包 + 安装说明   ← 排在 ③ 的内容层稳定后，约 0.5–1 天
⑤ 提交材料：作品链接 · 3 分钟 Demo 视频 · PPT · 源码仓库 · LearnBuddy 使用记录
```

> 时间：截止 **9/26 23:59**，初赛结果 9/30，决赛 10/15 线下。
> 「齐头并进」只适用于"内容层"，不适用于"两个前端各做一遍"。

## 3. 平台事实：Vercel

> **依据**：Vercel 官方文档 *Functions Limits* 与 *Limits*，**2026-09-18 逐条复核**。
> 标注 † 的条目**本次未能复核**，使用前请回查官方文档。

| 项 | 值 |
|---|---|
| 部署平台 | **仅 Vercel** |
| 函数区域 | **必须手动改**，默认 `iad1`（美东）；改为 **`hkg1`（中国香港）**，评委在深圳 |
| 函数区域数量 | **只能 1 个**（多区域仅 Pro / Enterprise 可用） |
| 单次函数执行上限 | **300 秒**（Hobby 默认 300 秒，**上限也是 300 秒**；Pro 可到 800 秒） |
| 内存 / CPU | **2 GB / 1 vCPU**（Hobby 的默认值与上限相同，**不可配**） |
| bundle 体积 | **解压后 250 MB**（含自动引入的 layer，由 AWS 强制）。**另有 Large functions 公测可到 5 GB**，见 §8 |
| 请求 / 响应 body | **4.5 MB**，超出返回 413 `FUNCTION_PAYLOAD_TOO_LARGE`，**基础设施层限制，改不了** |
| 文件描述符 | **1,024 个，所有并发执行共享**（含运行时自身占用）→ 官方明确建议**数据库用连接池** |
| 持久化文件系统 | **无**（可写目录只有 `/tmp`，见 §6.3） |
| 运行时日志 | **Hobby 仅保留 1 小时**（Pro 1 天，Enterprise 3 天） |
| 部署次数 | **100 次 / 天**（Hobby），另有 100 次 / 小时 的构建速率限制 |
| active CPU 计费 | **只算代码活跃消耗的 CPU 时间；等待 I/O（调模型、查库）不计入** |
| 缓存 | 每层 CDN 缓存 = 一次不计费的调用，**是免费额度里最值钱的东西** |
| 月度免费额度 | 100 万次调用 / 4 CPU-hrs / 100 GB 传输 / 360 GB-hrs 内存 † |
| Proxied Request Timeout | **120 秒**（官方通用限制表列出）——与函数 300 秒上限的关系未澄清，见 §8 |
| Docker | 不支持把自定义镜像作为函数运行时 † |

### 3.1 超时预算分档 `【已定】`（团队自定，非官方数字）

| 场景 | 上限 |
|---|---|
| 同步交互 | ≤ 30 秒 |
| 批处理单批 | ≤ 120 秒 |
| 任何单请求硬上限 | **≤ 180 秒**（Vercel 上限 300 秒，留 40% 余量） |
| 大模型单次调用 | ≤ 30 秒，**必须设超时** |

## 4. 技术栈与工程约束

### 4.1 技术选型 `【已定】`

> 依据：团队决策。**以下每一条都不是通过实验得出的，而是选型结论。**
> 其中"模型调用"一项已按 §4.2 第 4 条改为性质约束，不再锁定具体库（原因见 §6.5）。

| 用途 | 选型 |
|---|---|
| 全栈框架 | **Next.js（App Router）+ TypeScript**，Node `22.x`（`engines` 声明） |
| 界面 | Tailwind CSS + shadcn/ui |
| 服务端逻辑 | Route Handlers（`app/api/**/route.ts`）+ Server Actions（这就是后端，无需独立服务） |
| 模型调用 | 经**适配器层**封装，可替换；须支持流式与工具调用（具体实现见 §6） |
| 数据库 | Postgres（Neon / Supabase）—— **必须用连接池**（Neon `-pooler` / Supabase 6543 端口） |
| 向量检索 | pgvector（与 Postgres 同库，少一个外部依赖） |
| 对象存储 | Vercel Blob（客户端直传，免 CORS 配置） |
| 图谱可视化 | Cytoscape.js 或 react-force-graph |
| PDF 解析 | Node.js 侧库（如 `unpdf` / `pdf-parse`），必须在 Node runtime 跑 |

### 4.2 工程约束（逐条标注依据） `【已定】`

> **读法说明**：下表**只有第 3–6 条来自队友的实测经验**；第 1、2、7 条来自 Vercel 官方文档或
> 建仓时核实，第 8 条来自赛事手册。**不要把整节都当成实验结论。**

| # | 约束 | 依据 |
|---|---|---|
| 1 | **禁用 `export const runtime = 'edge'`** | Vercel 官方文档：Edge runtime **必须在 25 秒内开始发送响应**。至于"Edge 无流式优势"属团队判断 |
| 2 | **`content/**` 必须声明打包**，否则线上读不到、本地正常 | Next.js 的 `outputFileTracingIncludes`；与队友实测的同类机制（CLI 打包）互证 |
| 3 | **每个外部调用都必须有超时**（大模型 / 数据库 / 对象存储） | ✅ 队友实测经验 |
| 4 | **架构留缝**：外部依赖走适配器层，接口固定、实现可换；关键能力有降级 / 替代开关 | ✅ 队友实测经验（一天内换了两次模型调用方式，路由层与前端几乎没动） |
| 5 | **错误必须可见**：关键链路要有 `/api/ping` 类自检接口 + 结构化错误输出 | ✅ 队友实测经验（框架把真实错误包成一句无用的提示，靠自检接口定位） |
| 6 | **密钥管理**：一律环境变量；服务端专用变量用 `SERVER_` 前缀；`.env.local` 必须 gitignore；**绝不把读到的密钥写回文件**（含前缀） | ✅ 队友实测经验（曾发生覆盖真实密钥的事故） |
| 7 | **`LICENSE` 必须放仓库根**（MIT） | 赛事手册要求赛道二开源；**放子目录 GitHub 不识别**——建仓时核实 |
| 8 | **第三方库清单须在文档中注明** | 赛事手册 §8.2 |

第 2 条的写法：

```ts
// next.config.ts
outputFileTracingIncludes: {
  '/api/**': ['./content/**/*'],
}
```

每次往 `content/` 新增一级目录，**必须同步更新这份配置**。

## 5. 平台能力边界：专家 / Skill / 市场 / 客户端

> **依据**：《FPS 专家开发追踪文档》—— 队友用一个 FPS 数据教练专家做完整探路
> （该专家本身与本赛题无关，价值在其探测结论）。

### 5.1 四层结构 `【已核实】`

- **客户端**：提供运行环境与 agent 循环，**是一切的宿主**。
- **市场 marketplace**：带 `.codebuddy-plugin/marketplace.json` 的目录 / zip / git 仓库，负责**分发**。
- **专家 Expert**：市场里的一个条目，有身份、头像、可被用户主动选中。**＝"谁在做"（角色包）**。
- **Skill**：能力包，被 agent 按需加载，**没有身份**。**＝"怎么做"**。
  （`expertType: "agent"` 为单人专家；Team 型才有 `teamInfo` / `members` / `settings.json`。）

唯一交集：专家的 `plugin.json` 有 `skills` 字段，可预加载技能。

### 5.2 关键结论：没有服务端托管层，专家包给不出 URL `【推断】`

- 专家与 Skill 都是**本机资产**。链接能分发的只有"包"（zip / git 仓库），
  **能不能用取决于对方本地环境**。→ **发链接没用。**
- 别人要用你的专家 / Skill，需：装客户端 → 把包放进配置目录 → 改 `marketplace.json` → 重启。
- **据此推断**：答疑里"作品形态可以是 LearnBuddy 专家智能体"这条，
  **无法提供"作品链接"栏所需的地址** → 因此专家 / Skill 只能作为轨道 B（补充），
  **不能替代轨道 A**。（已列入 §7 待确认。）

### 5.3 若将来做"网页调本机能力"的桥 `【已核实】`

只有当网页需要调用**本机**能力时才需要桥。浏览器沙箱的三条硬边界：读不了本地文件、
起不了本地进程、跑不了 agent 循环。

安全红线（写死，不得违反）：
- 只绑 **`127.0.0.1`**，**永远不要 `0.0.0.0`**（否则同局域网任何人都能调你本机能力）
- 校验 `Origin` 头，只放行自己的域名
- 启动时生成随机 token，防其他本地页面偷调
- **不要用内网穿透把本地端口直接暴露公网**

> ⚠️ **适用范围澄清，防止误读**：本节结论**只适用于"浏览器 → 本机"这条路径**。
> 轨道 A 走的是**服务端在 Vercel 函数内直接跑 CodeBuddy Agent SDK**，属于另一条路径
> （见 §6.3）。**"必须自建本机桥"不构成对轨道 A 的否决。**

### 5.4 专家包结构与环境事实 `【已核实】`

```
<expert>/
├── .codebuddy-plugin/plugin.json   # 身份、展示名、头像路径、标签、推荐问法
├── agents/<name>.md                # 角色 prompt（人格与方法论）
├── avatars/expert.png              # 头像
├── README.md
└── .created-by-session
```

| 项 | 值 |
|---|---|
| 专家目录 | `$WORKBUDDY_CONFIG_DIR/plugins/marketplaces/my-experts/plugins/<name>/` |
| 市场源配置 | `$WORKBUDDY_CONFIG_DIR/plugins/known_marketplaces.json` |
| 配置目录 | **由 `WORKBUDDY_CONFIG_DIR` 决定**（官方文档写 `~/.workbuddy`，以实际为准） |
| 校验 / 注册 / 打包 | `validate_expert.py` / `register_expert.py`（**不跑则专家中心不可见**）/ `package_expert.py` |

> ⚠️ **已知文档不一致**：`expert-manager` 的 SKILL.md 写 `.workbuddy-plugin/`，
> 而脚本实际生成并校验的是 `.codebuddy-plugin/`。**以脚本行为为准。**

## 6. 运行时 AI 来源：风险与对冲

### 6.1 问题 `【待确认】`

| 约束 | 影响 |

### 6.2 对冲方案：`LLM_MODE` 双模式 `【已定】`

服务端模型调用经**适配器层**封装，用一个环境变量切换：

```
LLM_MODE 显式指定 > 有 SERVER_LLM_API_KEY 则 http > 否则 agent
```

| 模式 | 实现 | 用途 |
|---|---|---|
| `http` | 原生 `fetch` 打 OpenAI 兼容端点，自带 function calling 循环 | **开发期提效**（不消耗平台 Credits `【推断】`） |
| `agent` | `@tencent-ai/agent-sdk` + CodeBuddy CLI 打包进 Vercel 函数 | **评审演示期**，能力来自平台自身 |

**动作项**：演示 / 提交版本**必须切到 `agent` 模式**，或确保演示路径不出现第三方模型标识。
切换只是一个环境变量，**不需要重构**。

### 6.3 Agent SDK 在 Vercel 上跑通（探针实测） `【已核实】`

> ⚠️ **重要限定**：这是队友在一个**独立探针项目**（`agent-vercel-probe`）上的实测结果，
> **不是在本项目上验证的**。本项目复现之前，结论属于"平台层已验证、项目层待复现"。

| 项 | 值 |
|---|---|
| 结果 | 成功，`resultSubtype:"success"` |
| 耗时 | **7368 ms**（含 CLI 冷启动） |
| 环境 | linux x64 / Node **v24.19.0** / 工作目录 `/var/task` |
| 区域 | `hkg1`（`vercel.json` 的 `regions` 生效） |
| CLI | 启动成功，版本 `2.151.0` |
| 子进程 | ✅ 可用 |
| 可写目录 | `/tmp` 可写；`home` 目录**不存在** |

> ⚠️ 探针环境是 Node v24.19.0，**本项目锁 Node 22.x** → 复现时注意版本差异。

**三个必需配置（缺一不可）**：
1. `serverExternalPackages: ['@tencent-ai/agent-sdk']` —— SDK 不被打进 bundle
2. `outputFileTracingIncludes` 包含 SDK 的 `cli/` —— **把 CLI 二进制带进函数包**（否则线上找不到 CLI）
3. `HOME` / `TMPDIR` / `XDG_CONFIG_HOME` → `/tmp` —— Vercel 的 home 目录不存在，CLI 需要可写目录

> 注意第 2 条与 250 MB 解压上限的关系：CLI 会显著增大函数包，见 §8。

### 6.4 Agent SDK 的安全实践 `【已核实】`

- **务必 `tools: []` 关闭内置工具**，只暴露自己提供的工具。
  否则模型会获得**读写文件、执行命令**的能力——面向公网的 Web 应用里这是严重风险。
- 用 `allowedTools` 白名单放行自己的工具；`settingSources: []` 避免加载本地配置；
  `persistSession: false` 避免服务端写会话落盘。
- 工具暴露名形如 `mcp__<server>__<tool>`，前端展示时剥前缀。

### 6.5 依赖冲突 `【已核实】`

`@tencent-ai/agent-sdk` 要求 `zod ^4`，Vercel AI SDK v4 要求 `zod ^3` → **无法共存**。

处理顺序：能统一就统一 → **统一不了先想"是不是可以不用它"**
（HTTP 模式已用约 200 行原生 `fetch` 实现 function calling 循环，反而更可控、零版本风险）
→ 最后才考虑 `--legacy-peer-deps`（会埋运行时隐患，不推荐）。
