## 0. 一句话结论

**CloudBase 作为"数据库"完全可用（走 HTTP API，不是 `pg` 协议）；作为"能跑 AI 的云函数宿主"也已实测跑通**
（CodeBuddy CLI 在云函数里起来并调通了真实 API）。**两个用途都成立，但代价不同**：
数据库这条路几乎没有代价；把 AI 放进 CloudBase 云函数则要接受**单次约 35 秒延迟**与**内存只剩约 50MB 余量**。

## 2. 数据库（P0）

### 2.1 `pg` 协议公网直连 → ❌ **不可行** `【已实测】`

- 控制台「配置 → 网络配置」：**「外网 IPv4 地址」为"暂无"**，悬停提示：
  「当前共享集群暂不提供相关能力，可以升级至独享集群启用能力」
- 环境详情确认 `TenantType: SHARED`
- 官方定价文档原文：**「独享实例需企业版及以上才可开启」**（企业版 ¥999/月，限时 ¥799.2/月）

**结论：不是配置没开，是套餐能力边界。** 比赛期间不可能为此升级企业版。
→ **Vercel 等公网服务端无法用 `pg` / 连接串方式连接这个数据库。**

### 2.2 HTTP API（PostgREST）→ ✅ **全链路可用** `【已实测】`

- **网关地址**：`https://<envId>.api.tcloudbasegateway.com`
- **认证**：`Authorization: Bearer <API Key>`
  （API Key 在「环境管理 → 环境配置 → API Key」创建，**属服务端管理员级权限，绝不能进前端**）
- **表操作路径**：`/v1/rdb/rest/<表名>`（PostgREST v15 风格）

**从本地（深圳）实测的完整增删改查**（表 `public.cb_probe`）：

| 操作 | HTTP 方法 | 状态 | 耗时 |
|---|---|---|---|
| 读表 | GET | 200 | 194 ms |
| 插入 | POST | 201 | 131 ms |
| 条件查询 | GET | 200 | 81 ms |
| 计数 | GET | 200 | 79 ms |
| 更新 | PATCH | 200 | 57 ms |
| 删除 | DELETE | 204 | 62 ms |

**认证是否通过的判据**：未带 Key 会被 401 拦；带 Key 但表不存在会返回
`DATABASE_PGRST205: Could not find the table 'public.<表名>' in the schema cache`
——**这条错误恰恰证明认证通过、路由正确、真的查到了库**。

**优点**：无状态。**不需要连接池，不占文件描述符**，天然适合 Serverless。

**限制**：
- **公网 HTTP 网关只提供 REST / RPC，没有 SQL 入口**（`/v1/rdb/sql`、`/v1/rdb/query` 均 404）。
  ⚠️ **注意区分**：**建表 / 改 schema / 跑任意 SQL 是能做到的** —— 通过平台的管控面
  （控制台 SQL 编辑器、CloudBase CLI 的 `tcb db pg`、或客户端内置连接器的 `managePgDatabase` / `queryPgDatabase`）
  都可以执行 DDL 与只读查询。**缺的只是"从公网用 HTTP 直接发 SQL"这一条**，日常开发不受影响。
- 复杂 JOIN / 事务 / 全文检索等需要包装成 RPC 函数
- 匿名登录路由存在，但需要 `设备id` 请求头

→ 如果打算用 CloudBase 静态托管**给评委一个能直接点开的链接**，必须先解决这个中间页 / 备案问题。

## 3. 云函数（P1）

测试函数：`diagnose`（Event 型 / Nodejs18.15 / 256MB 内存 / 0.2 核 / 512MB 磁盘 / InitTimeout 65s）

### 3.1 超时 → ✅ **可以调到 300 秒** `【已实测】`

**官方套餐文档写「免费体验版云函数超时 3s，不支持修改」——实测不成立。**

| 步骤 | 结果 |
|---|---|
| 创建时设 `timeout=20` | 被接受（详情返回 `Timeout: 20`） |
| 调用时睡 25 秒 | ❌ 失败：`Invoking task timed out after 20 seconds`，Duration **20000ms** 精确掐断，statusCode 433 |
| `updateFunctionConfig timeout=300` | **被接受** |
| 再调用睡 35 秒 | ✅ **成功**（Duration 38290ms，`survived: true`） |

→ **超时严格按配置值执行，且免费版即可设到 300 秒。**
`【待验证】`：能否设到 900 秒（个人版/标准版官方上限）；HTTP 型函数是否同样放开。

### 3.2 子进程能力 → ✅ **完全可用，且 node + npm 都在** `【已实测】`

| 探测 | 结果 |

### 3.6 HTTP 型函数的额外要求 `【已实测】`

创建时 `type: "HTTP"` 会失败：
`ResourceNotFound.BootstrapFile ... Unzip entryfile Failed, filename not matched: scf_bootstrap`
→ **HTTP 型云函数必须自带 `scf_bootstrap` 启动脚本**（要自己起 HTTP 服务，监听 9000 端口）；
用 `type: "Event"` 才是"zip + `exports.main`"的传统形态。

### 3.7 ⚠️ 安全事实：运行时自动注入临时密钥 `【已实测】`

函数进程的环境变量里**自动包含**：
`TENCENTCLOUD_SECRETID` / `TENCENTCLOUD_SECRETKEY` / `TENCENTCLOUD_SESSIONTOKEN`
（SCF 默认行为，配合角色 `TCB_QcsRole`）

**含义**：函数内代码天然持有云 API 权限。**若把函数暴露到公网且能执行任意代码，等于把账号权限挂出去。**
→ 面向公网时必须：限制入参、不暴露任意代码执行、按最小权限改造角色。
（本次探针**只输出变量名，未输出任何值**。）

## 4. 「CloudBase 能不能跑 CodeBuddy CLI」——体积测算与实测

### 4.1 ✅ **已实测：SDK 打进云函数并跑通（P2，2026-09-19 00:40）**

**结论：CloudBase 能跑 CodeBuddy CLI —— 端到端调通，返回了真实模型输出。**

配置：Event 型 / **`Nodejs20.19`** / `timeout: 300` / `InstallDependency: true`（依赖由平台侧安装）

| 步骤 | 结果 |
|---|---|
| 运行时 Node | **v20.19.3** ✅（满足 CLI 最低要求 ≥18.20.8） |
| SDK 安装 | ✅ 平台侧自动装成功：`/var/user/node_modules/@tencent-ai/agent-sdk@0.3.262`，**151.7 MB / 2815 文件**（与 npm 元数据完全一致） |
| CLI 定位 | ✅ `cli/bin/codebuddy`（14,056 B），`cliPackageVersion 2.154.0`，headless dist 存在 |
| `node cli/bin/codebuddy --version` | ✅ exit 0，stdout `2.154.0`，**286 ms** |
| **真实 API 调用** `codebuddy -p "只回答两个字：收到"` | ✅ **exit 0，stdout `收到`**，**37.1 s** |
| 第二次调用（同实例） | ✅ stdout `可用`，**34.6 s** |
| 峰值内存 | **197–208 MB / 256 MB** |
| 函数总耗时 | 37.5 s / 34.9 s（远低于 300 s 上限） |

**⭐ 环境变量：Vercel 那套做法在 CloudBase 上必须改一处**

- 平台侧**可设**：`CODEBUDDY_API_KEY`、`CODEBUDDY_INTERNET_ENVIRONMENT=internal`
- ⚠️ **`HOME` 不能作为函数环境变量注入** —— 平台直接拒绝：
  `[CreateFunction] 不支持修改函数系统环境变量和运行环境变量(HOME)`
  → 改为**在函数代码里设 `process.env.HOME = '/tmp'` 并注入给 spawn 的子进程**；
  `TMPDIR` / `XDG_CONFIG_HOME` 同批处理。**实测同样奏效。**
- `【待验证】`：`TMPDIR` / `XDG_CONFIG_HOME` 是否也被平台单独拒绝（本次与 `HOME` 一起去掉，未逐个验证）

**⚠️ 两个必须记住的代价**

1. **单次响应约 35 秒**（普通 prompt，**不是**冷启动造成的 —— 第二次仍 34.6s）。
   评委体验上是明显等待 → 演示前必须预热，或改用流式输出 / 更短的调用链。
2. **内存吃到 198–208 MB，只剩约 50 MB 余量**；免费版内存**固定 256 MB、不支持修改**。
   多步 agent / 长上下文有 OOM 风险 → 要加内存需升**个人版（¥19.9/月）**。

`【待验证】`：流式输出（SSE）是否可用；多轮 / 多步任务的内存与耗时；用 `scf_bootstrap` 暴露成 HTTP 接口的完整链路。

> 测试函数 `sdkprobe` 已在测完后**立即删除**（它持有 `CODEBUDDY_API_KEY` 环境变量，不留存）。

## 5. 结论与建议

### 5.1 两条路的能力对照

| 维度 | CloudBase 云函数 | Vercel 函数 |
|---|---|---|
| 跑 CodeBuddy CLI | ✅ **已实测** | ✅ 队友已实测 |
| 单次延迟（普通 prompt） | **约 35 s** | **约 7.4 s** |
| 内存 | 256MB 固定（免费版），实测余量仅 ~50MB | 2 GB，宽裕 |
| 超时 | 可设 300 s（实测） | 300 s |
| 运行时 Node | 18.15 / **20.19**（无 22） | 22.x |
| 国内可达性 | ✅ 上海 | ❌ `*.vercel.app` 有污染风险 |
| 部署方式 | 控制台 / CLI / 连接器（**无 Git 自动部署联动**） | Git 推送自动部署 |
| 数据库 / 认证 / 存储 | **自带**（PG + RLS + 认证 + 对象存储 + pgvector） | **都没有**，需外部服务 |

### 5.2 推荐组合：主体 Vercel + 数据库 CloudBase

**理由**：
1. **把 AI 留在 Vercel** —— 35 s vs 7.4 s 的差距直接决定评委体验；Vercel 内存宽裕，不担心多步 agent OOM。
2. **把数据放 CloudBase** —— 免费额度按"HTTP 调用 30 点/万次"算，**3000 点/月 ≈ 100 万次调用**，
   演示量级绰绰有余；且共享实例"无访问时不产生计算用量"，成本可控。数据留在腾讯云，也省掉另开 Neon/Supabase。
3. **pgvector 已验证可用**，向量检索需求不需要额外引入第三方向量库。

**但必须同时落实三个前提**：

1. ⚠️ **数据访问层必须走适配器**（项目本来就要求"外部依赖走适配器层"）。
   因为 `pg` 直连在此环境**不可用**（§2.1），只能用 HTTP/PostgREST。
   适配器化之后，将来要换成标准 Postgres / 正式环境，只改一个文件。
2. ⚠️ **API Key 是管理员级权限**（§2.2）。它要放在 Vercel 的服务端环境变量里 →
   等于把腾讯云这段权限交给 Vercel。建议：**优先用 RLS + 最小权限账号**，而不是长期用管理员 API Key；
   并确认 `SERVER_` 前缀、`gitignore`、不进前端这三条底线。
3. ⚠️ **"数据库放哪里"与"评委能不能打开链接"是两件事**。
   这个组合**不解决** `*.vercel.app` 在大陆的可达性（评委打开的还是 Vercel 域名）。
   如果要覆盖这个风险，需要**单独决策**：绑自有域名 / 备一份国内可达的演示页（注意 §2.5 的中间页与备案问题）。
4. ⚠️ **开发期注意响应延迟**：Vercel 函数在中国香港、数据库在上海 → 跨公网每次查询有额外往返 `【待验证】`。
   若发现明显变慢，可考虑把函数区域也设在中国香港（已是计划内），并尽量合并查询。

### 5.3 澄清：这次的实质是「换数据库供应商」，不是「从没有到有」

**先纠正一个容易有的误解**：原来的 Vercel 方案**一直是有数据库的** —— 只是 **Vercel 本身不提供数据库**，
所以原方案是**外接第三方 Postgres**。原文依据出自**当时的《项目决策记录》**（该文件已于 2026-09-19 删除；以下为它的原文，历史版本见 git 记录）：

- `docs/项目决策记录.md` **§4.1**：`| 数据库 | Postgres（Neon / Supabase）—— 必须用连接池（Neon -pooler / Supabase 6543 端口） |`
- 同处：`| 向量检索 | pgvector（与 Postgres 同库，少一个外部依赖） |`
- `docs/项目决策记录.md` **§3**：`| 文件描述符 | 1,024 个，所有并发执行共享 → 官方明确建议数据库用连接池 |`
- `docs/傅加贝/建议2.md` 的对照表：数据库一栏即 **「CloudBase 文档数据库」 vs 「Neon/Supabase PostgreSQL」**；
  该文并指出 Vercel 方案的运维组件是「Vercel + 数据库 + Blob 等**多个平台**」，风险里明确列了「网络、打包体积、**连接池**和函数限制」，
  缺点里写「Serverless 数据库连接更复杂，**必须使用连接池**，还要考虑冷启动、连接数和**数据库区域与函数区域的距离**」。

**因此，引入 CloudBase 数据库 = 换一个供应商，而不是补一个缺失的部件。**

| 维度 | Neon / Supabase（原方案） | CloudBase PostgreSQL（本次评估） |
|---|---|---|
| 访问方式 | 标准 `pg` 协议**直连** | ❌ 共享实例**不能直连**（§2.1），只有 HTTP / PostgREST |
| 连接池 | **必须**（Vercel FD 1,024 那条约束） | **不需要** —— HTTP 无状态，天然适配 Serverless |
| 事务 / 复杂 SQL | 完整 | 受 PostgREST 限制，需包装成 RPC 函数 |
| pgvector | 需自行开启 | ✅ 已验证可用（0.8.2，§2.3） |
| 区域 | 可选（如新加坡），需与函数区域匹配 | 上海 |
| 数据位置 | 境外 | 腾讯云境内 |
| 生态 | 第三方 | 腾讯自家，与赛事背景一致 |
| 费用 | 有免费层（额度未核 `【待验证】`） | 免费体验版 3000 点/月（§2.4） |

**结论**：
- 换 CloudBase 的**主要代价**是「数据访问方式从标准 SQL 变成 REST」→ 这正是 §5.2 第 1 条要求**数据访问层必须适配器化**的原因
  （否则将来想换回去会很痛）。
- 换 CloudBase 的**主要收益**是「省掉连接池这套复杂度 + 数据留在境内 + 与腾讯生态一致」。
- ⚠️ **反过来也成立**：**继续用 Neon / Supabase 是一个完全成立的选择** —— 原方案本来就是完整可用的，
  CloudBase 不是必需品。不要把它当成"没有数据库所以要补一个"。

### 5.4 不推荐的做法

- ❌ **把整个应用搬到 CloudBase**：技术可行（已实测），但要接受 35 s 响应 + 内存余量 50MB，
  且丧失 Vercel 的 Git 自动部署与宽裕内存 —— **收益（国内可达）与代价不成比例**，
  除非愿意同时升个人版（¥19.9/月）换取更大内存，并自己解决 HTTP 暴露（`scf_bootstrap`）。
- ❌ **依赖 CloudBase 云托管跑 CLI**：按小时计费，1核2G ≈ ¥86/月，免费额度完全撑不住。
- ❌ **用 CloudBase 静态托管的默认域名当正式作品链接**：见 §2.5，有中间页且生产环境要求自定义域名（需备案）。

## 6. 遇到的环境坑（可复用）

| # | 现象 | 原因 | 对策 |
|---|---|---|---|
| 1 | `tcb login` 报「配置文件必须包含环境 Id」 | CLI 会强制校验 cwd 下的 `cloudbaserc.json`，envId 留空即报错 | 登录前先把 `cloudbaserc.json` 改名（如 `cloudbaserc.json.tpl`） |
| 2 | 设备码登录过期 | **设备码有效期仅几分钟** | 先建好环境，再当场授权 |
| 3 | CLI 授权页只显示「暂无可用环境」 | **CLI 授权必须绑定一个已存在的环境** | 顺序必须是"先建环境 → 再授权" |
| 4 | `createFunction` 报 `additionalProperties` | 管控面接口的 `func` 不接受 `memorySize` 字段 | 去掉该字段（免费版内存本就固定 256MB） |
| 5 | `createFunction type:"HTTP"` 报 `ResourceNotFound.BootstrapFile` | HTTP 型函数需要 `scf_bootstrap` | 用 `type:"Event"` |
| 6 | `createFunction` 报「不支持修改函数系统环境变量和运行环境变量(HOME)」 | **平台禁止覆盖 `HOME`** | 改为在函数代码里 `process.env.HOME='/tmp'` 并注入子进程 |
| 7 | `updateFunctionCode` 报 `FUNCTION_UPDATING` | 上一次代码更新还在进行中（SCF 在 Updating 期间拒绝写操作） | 等 10 秒且 `Status=Active` 后再重试，**不要连打** |
| 8 | 60MB 可压缩文件通过了体积测试 | `CodeSize` 记录的是**压缩后**体积（60MB → 275KB） | 测体积上限必须用**不可压缩的随机数据** |
| 9 | 用 `require.resolve('…/package.json')` 定位包失败 | 该 SDK 的 `exports` 未暴露 `./package.json` | 改为 resolve 主入口，再向上找 `package.json` |
| 10 | Git Bash 里没有 `sleep` / `du` | 本机 Git Bash 是精简环境 | 等待改用 `node -e "setTimeout(()=>{},3000)"` |
| 11 | `rm -rf` 被拦截 | 本机有安全删除机制 | 改用 `node -e "fs.rmSync(...)"` 或逐文件 `fs.unlinkSync` |
