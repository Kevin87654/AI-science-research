## 0. 一句话结论

**可以开工，但有三条硬约束必须先写进设计，否则代码写完要返工。**

1. **单次数据库请求硬上限 8 秒** —— 网关层限制，SQL 里改不掉（函数内 `set_config` 覆盖无效，已实测）。"同步交互 ≤30s"这类预算不可用。
2. **API Key 是 `service_role`，带 `bypassrls = true`** —— **RLS 对它完全不起作用**。"按用户隔离"只能靠应用层，数据库不会替你兜底。
3. **不建 RLS 的表，任何低权限凭据（`anon`）都能读全表** —— 已实测：`anon` 角色读到了没开 RLS 的表里全部 5 行数据。

另外确认了两件此前标"未验证"的事：**RPC 路径可用**（`/v1/rdb/rest/rpc/<函数名>`），**事务可以通过 RPC 包装实现**。

## 1. 接入姿势（可直接照抄）

| 项          | 结论                                                                   |
| ---------- | -------------------------------------------------------------------- |
| 网关         | `https://kevin-cloud-server-d8c078fa24b09.api.tcloudbasegateway.com` |
| 表操作        | `GET/POST/PATCH/DELETE  <网关>/v1/rdb/rest/<表名>`                       |
| **RPC 调用** | `<网关>/v1/rdb/rest/rpc/<函数名>` ✅ **已实测可用**                             |
| 鉴权         | **只有 `Authorization: Bearer <API Key>` 这一种** `【已实测】`                 |
| 其他鉴权写法     | `apikey: <key>` 头 → 401；`Authorization: <key>`（不带 Bearer）→ 401       |
| 公网 SQL 入口  | ❌ 不存在。`/v1/rdb/sql` → 404 `INVALID_PATH`；DDL 走连接器 / 控制台              |
| 二进制 / 文件   | 不走这里（PG 模式用 pgstore，另见交接说明）                                          |

**判据提示**：带 Key 但表不存在会返回 `DATABASE_PGRST205 Could not find the table 'public.xxx' in the schema cache` —— **这条错误恰好证明鉴权通过、路由正确**。

## 2. 硬约束表（会直接改变设计）

| # | 约束              | 数值                                                                                                  | 影响                                                                                          |
| - | --------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1 | **单条 SQL 语句超时** | **8 秒**（`statement_timeout = 8s`，`lock_timeout = 8s`）`【已实测】`                                        | **任何**数据库操作必须 8s 内完成。超过 → 500 `DATABASE_57014 canceling statement due to statement timeout` |
| 2 | 能否在函数内放宽        | ❌ **不能**。函数内 `set_config('statement_timeout','60s',true)` 后 sleep 12s / 20s，仍在 **8.1s** 被掐断 `【已实测】` | 限制在**网关/代理层**，不在角色 GUC 上，SQL 无解                                                             |
| 3 | API Key 权限      | `role: service_role`，`rolbypassrls = true` `【已实测】`                                                  | RLS 形同不存在，隔离必须应用层做                                                                          |
| 4 | 无 RLS 的表        | 低权限角色可读全表（实测 `anon` 读到 5/5 行）`【已实测】`                                                                | **每张业务表都必须显式开 RLS**                                                                         |
| 5 | 请求体大小           | 6 MB 仍 201 通过，**未找到上限** `【待验证】`                                                                     | 实际瓶颈是 Vercel 的 4.5 MB                                                                       |
| 6 | 浏览器直连           | 带 `Origin` 且不在安全域名白名单 → **403（空正文）** `【已实测】`                                                        | 服务端调用不带 Origin，正常；**浏览器调用会被拦**                                                              |
| 7 | 错误正文            | DB 原文透传（含表名/列名/约束名）`【已实测】`                                                                          | API 层**必须**改写错误，不能直传                                                                        |
| 8 | 请求头对 SQL 可见     | `request.headers` 里**含 `authorization`（即调用方 API Key）** `【已实测】`                                      | 任何 RPC 都能读到 Key → **禁止把它写进日志/返回值**                                                          |

**安全域名实测** `【已实测】`：`example.com` / `127.0.0.1:3000` / Vercel 域名 → 403；`localhost:3000` → 200；`<envId>-1437126399.tcloudbaseapp.com` → 200。  
→ 本架构是**服务端调数据库**，不带 Origin，不受影响。这条反而是一层额外保险：**Key 即使误进前端，浏览器也调不通**。

## 3. 数据面能力清单

### 3.1 可用 ✅（全部实测通过）

| 能力         | 用法                                                                                                     | 结果                                     |
| ---------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 单行 / 批量插入  | `POST /<表>`，body 为对象或数组                                                                                | 201                                    |
| 写入后拿回整行    | `Prefer: return=representation`                                                                        | 201 + 行                                |
| 不返回正文      | `Prefer: return=minimal`                                                                               | 201 / 204                              |
| **upsert** | `Prefer: resolution=merge-duplicates` + body 带主键                                                       | 首次 201、再次 200，值被覆盖                     |
| 投影         | `?select=label,score`                                                                                  | 200                                    |
| 排序 / 分页    | `?order=score.asc&limit=2&offset=1`                                                                    | 200                                    |
| 精确计数       | `Prefer: count=exact` → 响应 **206** + `content-range: 0-0/3`                                            | 200 / 206                              |
| 单对象响应      | `Accept: application/vnd.pgrst.object+json`                                                            | 200；**命中多行 → 406 `DATABASE_PGRST116`** |
| 过滤操作符      | `eq` `neq` `gt` `gte` `lt` `in.(a,b)` `like.*x*` `is.null` `cs.{x}`（数组包含） `payload->>c=eq.值`（jsonb 路径） | 全部 200                                 |
| 更新         | `PATCH /<表>?<过滤>`                                                                                      | 200 / 204                              |
| 删除         | `DELETE /<表>?<过滤>`                                                                                     | 204                                    |
| HEAD       | `HEAD /<表>?select=id` + `Prefer: count=exact`                                                          | 200 + `content-range: 0-4/5`           |

### 3.2 不可用 / 有坑 ⚠️

| 项                     | 实际情况                                                                                                                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **非 `public` schema** | ❌ **完全不可达**。默认查 → 404；`Accept-Profile: probe_test` → **406 `DATABASE_PGRST106 Invalid schema`**；路径写 `probe_test.表` → 被拼成 `public.probe_test.cb_schema_probe` → 404。`【已实测】` |
| **`PATCH` 不带过滤条件**    | ⚠️ **合法且会更新整张表**，无任何确认机制。Repository 层必须强制要求过滤条件                                                                                                                            |
| **`Range` 头分页**       | 行为不直观：`Range: 1-2` + `limit=2` 只回 1 行（`content-range: 1-1/*`）。**用 `limit`/`offset`，别用 Range**                                                                              |
| **volatile 函数走 GET**  | ⚠️ 预期应被拒，实际 **200 且真的执行了**（`cb_sleep_probe` 走 GET 睡了 1 秒）。→ 别把有副作用的函数暴露成可 GET                                                                                              |
| 复杂 JOIN               | 受 PostgREST 限制，需包装成 RPC 函数（可做，见 §7）                                                                                                                                        |
| 连接池                   | 不需要（HTTP 无状态），网关侧自己复用连接                                                                                                                                                    |

## 4. 类型与编码 `【已实测】`

- **中文 / emoji / 单双引号 / 反斜杠 / 换行 / 制表符** 全部原样往返，无转义问题
- `jsonb` 深层嵌套（`null`、数字、中文混排）往返正确
- `numeric(6,2)` 正常；溢出（给 12345.67）→ 400 `DATABASE_22003 numeric field overflow`
- `text[]` 数组往返正确，支持 `cs.{x}` 包含查询
- `timestamptz` 返回形如 `2026-09-20T15:59:38.464203+08:00`（**+08:00 偏移**），库时区 `PRC`
- `uuid` + `gen_random_uuid()` 默认值正常
- 类型 / 约束错误一律 400：NOT NULL 违约、未知列、类型不匹配、畸形 JSON body 都是 400（**不是 500**）

## 5. 错误形态与信息泄漏面 ⚠️

**统一返回结构**（网关层）：`{"code": "...", "message": "...", "requestId": "..."}`

| 场景                             | 状态      | code                                                   |
| ------------------------------ | ------- | ------------------------------------------------------ |
| 无鉴权                            | 401     | `MISSING_CREDENTIALS`                                  |
| 鉴权无效                           | 401     | `INVALID_CREDENTIALS`                                  |
| 表不存在                           | 404     | `DATABASE_PGRST205`                                    |
| 函数不存在                          | 404     | `DATABASE_PGRST202`                                    |
| 路径不对（如 `/v1/rdb/sql`）          | 404     | `INVALID_PATH`                                         |
| **路径前缀错**（`/v1/rdb/restx/...`） | **500** | `SYS_ERR`（≈ 给 404 更合理，但它给 500）                         |
| 单对象但命中多行                       | 406     | `DATABASE_PGRST116`                                    |
| schema 不在白名单                   | 406     | `DATABASE_PGRST106`                                    |
| 数据 / 约束 / 类型错误                 | 400     | `DATABASE_22xxx` / `DATABASE_42703` / `DATABASE_P0001` |
| 语句超时                           | 500     | `DATABASE_57014`                                       |
| 浏览器 Origin 未白名单                | **403** | 空正文                                                    |

> ⚠️ **`message` 字段是数据库原文**，实测泄漏过：表名（`public.no_such_table_xyz`）、列名（`cb_rls_probe.does_not_exist`）、以及我们自己 `raise exception` 的文本。  
> → `/api/*` **必须做错误映射**，对外只给中性文案 + 自建 requestId。

## 6. 身份与权限（本文最重要的一节）

### 6.1 从 SQL 内部看到的身份 `【已实测】`

用 RPC 函数读 `current_user` / `current_setting('request.jwt.claims')` / `request.headers`：

```
current_user   = service_role
session_user   = cloudbase_authenticator      ← PostgREST 用固定角色连接后 SET ROLE
bypassrls      = true                          ← 关键
jwt_claims     = {"role":"service_role","aud":"<envId>","app_metadata":{"provider":"apikey"}, ...}
timezone       = PRC
search_path    = "public", "public"
```

### 6.2 同一张 RLS 表、两种角色的对照 `【已实测】`

表 `cb_rls_probe` 已 `ENABLE + FORCE ROW LEVEL SECURITY`，策略要求 `owner_id` 等于 `jwt_claims->>'sub'`（API Key 场景下为空 → 策略恒不匹配）：

| 角色                          | 读到的行数                        |
| --------------------------- | ---------------------------- |
| 我们的 API Key（`service_role`） | **3 行全读到**，且能写入任意 `owner_id` |
| `anon`                      | **0 行**（策略正确生效）              |

**结论**：

- **RLS 机制本身是好的**（`anon` 那侧验证有效）；
- 但我们用的 Key 带 `BYPASSRLS`，**它对我们等于不存在**；
- 所以"两个匿名用户互相看不见"**只能靠 Repository 层每次都带归属过滤**，并用"伪造他人标识"的测试用例守住。

### 6.3 另一个坑：不开 RLS 的表是敞开的 `【已实测】`

`cb_type_probe`（探针新表，**没开 RLS**）：`anon` 角色 **读到了全部 5 行**。  
→ **每张业务表都要显式 `enable row level security`**，哪怕我们自己在用管理员 Key。这是防止"以后引入 CloudBase Auth / 浏览器端凭据"时数据直接裸奔。

### 6.4 自定义请求头能透传到 SQL `【已实测】`

实测 `x-our-session`、`x-user-id`、`x-cloudbase-session` **都出现在 `request.headers` 里**（`origin` 则不透传）。

**可用价值**：匿名会话 Token 可以随请求头下传，然后在 SQL 里做  
`current_setting('request.headers', true)::jsonb ->> 'x-session-hash'` 的 RLS 兜底。  
⚠️ **但它是可伪造的**（能发请求的人就能改头），所以**只能当"防自己写漏 WHERE"的第二道保险，不能当主控制**。

### 6.5 ⚠️ 必须知道的暴露面

`request.headers` 里**包含 `authorization`**，也就是**调用方的 API Key 对任何 SQL 函数可见**。  
→ 每个 RPC 里**绝对不能**把 `request.headers` 整体打日志或塞进返回值。

## 7. 事务：可以用，但要换写法 `【已实测】`

REST 没有事务语义。实测用 **plpgsql 函数包装多步写入**：

```
先插 step=1 → 再插 step=2
  成功路径：返回 {a:1,b:2}，表里 2 行          ✅ 200
  失败路径（中间 raise exception）：返回 400，表里 **0 行**  ✅ 整体回滚
```

**结论**：需要原子性的多步写入（如"建会话 + 建初始进度"）**写成 RPC 函数**，不要用两次 REST 调用拼。

## 9. 迁移流程实测（含一处流程偏差）

**能做**：`applyMigration` 建表 / 建函数 / 建 policy 全部成功，本轮 5 条迁移全部落库并经 `listMigrations` 确认。

**规则**（实测确认）：

- `migrationVersion` 必须是 **14 位时间戳** `YYYYMMDDHHMMSS`
- `migrationName` **只能小写字母 + 下划线，不能含数字**
- 必须显式 `confirm: true`
- `waitForTask: false` 时返回 `TaskId`，**必须**再用 `describeMigrationTask` 看 `Status/Phase/Reason`，再用 `listMigrations` 确认落库 —— 只看到任务受理**不等于**已应用
- 建表 / 改 schema 必须走 `applyMigration`；`execute` 只用于 DML / GRANT / RLS

**⚠️ 流程偏差**：`applyMigration` 返回的 `localFileHint` 写的是仓库路径 `cloudbase/migrations/<version>_<name>.sql`，  
但**实测文件没有写进仓库** —— 它落在 **AI 助手的 MCP 运行目录**（`~/.learnbuddy/logs/mcp-runtime/` 下，不在项目内）。  
→ 「源文件 vs 投递记录」两套目录，**投递记录那一半不会自动进仓库，必须手动搬**。

## 10. 对数据访问层设计的直接结论

| #  | 结论                                | 动作                                                                    |
| -- | --------------------------------- | --------------------------------------------------------------------- |
| 1  | **单请求 ≤ 8s**                      | 每次调用设客户端超时（建议 6s）；**服务端超时预算按 8s 硬顶**设计                                |
| 2  | **RLS 不保护我们**                     | **每个** Repository 查询强制带 `owner_id` 过滤；加"伪造他人标识"回归测试                   |
| 3  | **每张业务表都要开 RLS**                  | 建表脚本里统一 `enable row level security`（可选再加"需带会话头"的兜底策略）                 |
| 4  | **错误必须改写**                        | 统一映射成自己的 `{ok:false,error:{code,message,requestId}}`，不透传 `DATABASE_*` |
| 5  | **复杂 / 原子写走 RPC**                 | 建表时规划好需要的函数（如"建会话 + 初始进度"）；RPC 路径已验证可用                                |
| 6  | **用 `limit`/`offset`，不用 `Range`** | 分页实现按此写                                                               |
| 7  | **不要用非 `public` schema**          | 见 §3.2；测试数据改用"标记 + Repository 过滤"                                     |
| 8  | **`PATCH`/`DELETE` 必须带过滤条件**      | Repository 接口设计上就不给"全表更新"的入口                                          |
| 9  | **RPC 里不许碰 `request.headers`**    | 它会带出调用方的 Key；代码评审要卡这条                                                 |
| 10 | **浏览器永远不直连数据库**                   | 既是架构要求，也被网关 Origin 白名单天然挡住                                            |
